# Agent 本人单据检索与指定草稿办理设计

**状态：用户已确认；实现已提交，双员工现场验收待执行（2026-10-27）**

## 意图、目标和边界

员工希望在飞书私聊或 Web 私有 Agent 会话中，按条件、指定数量查找本人单据，选中明确的草稿继续编辑、管理票据、排除提交阻断并确认提交；还应能查询当前可核实的处理进度。此前只显示最近五单和只读选择，查询旧单后不能编辑，给正在办理的草稿上传附件也不能指定目标。目标是形成“查找—辨认—办理—提交—跟进”的完整员工路径，同时让 React Web 工作台与 Agent 读取同一个 Go 报销事实源。

本期纳入：本人多条件搜索、指定数量和排序、分页及总数；精确单号查找和显式办理目标；指定本人草稿的四字段修改、票据列表/上传/删除后重传、提交校验与两阶段确认；草稿删除；可核实的单据、OCR、人工复核及提交进度和必要通知；身份、版本、幂等、审计、隐私保护。已有当前 Intake 的创建和办理路径必须继续可用。

不纳入：跨员工查询或代办、群聊展示个人单据、多币种、Agent 代填申请金额/币种/备注、自动提交、自由模型工具调用、真实审批和付款业务。Go 当前只有 `DRAFT`、`SUBMITTED` 两种单据状态；审批、付款只预留版本化进度投影/事件接入点，不产生虚构状态、按钮或通知。用户问及未接入的阶段时明确说“当前系统未接入审批/付款进度”。

## 既有架构选择与取舍

沿用已获用户确认的 **结构化模型意图 + 确定性 Agent 工具网关 + Go 领域服务**。模型只提取动作、目标指代和查询条件；Go 根据已认证员工执行本人查询、草稿写入、校验、审计和事件发布。Web 和飞书适配同一套会话用例与工具契约。

- **采用：扩展 Go 本人搜索接口及受控办理工具。** 数据库先按员工和条件筛选，再排序/计数/分页；Agent 保存最少量搜索与目标上下文，绝不把前 100 单拉到模型里筛选。代价是涉及 Go、OpenAPI、Agent、会话迁移和消息测试，但能保证旧单不会因截断而漏查。
- **不采用：只把 Agent 的固定五条改成模型指定 `limit` 并在 Node 过滤。** 当前 Go 接口最多返回 100 条且无分页；金额/日期过滤会产生不完整结果，模型也不能可靠承担权限与业务筛选。
- **不采用：把最近一次只读选择直接变成写入目标，或放开模型直接调用任意 HTTP/MCP 工具。** 两者都可能把“查这张”误当“改这张”，绕过现有 Intake、版本和确认边界。

## 员工可见的操作约定

| 员工表达 | 期望结果 |
| --- | --- |
| “查上个月草稿，按金额从高到低列 12 张” | 回显筛选条件和匹配总数；按请求顺序展示首批，余下按游标回复“下一页”。 |
| “上个月交通费一共几张” | 只返回符合条件的本人单据总数，不误报展示条数为总数。 |
| “查 BX20261024-0004” | 本人精确查询，并设为只读目标；不更改当前办理草稿。 |
| “编辑 BX20261024-0004” | 本人、草稿核验后设为办理目标，回复单号、事由和可执行动作；原有 Intake 草稿保留，不隐式删除或提交。 |
| “把事由改成客户拜访” | 仅对明确的办理目标执行，回复完整单号和 Go 回读的保存值。若刚查询了另一张单，先澄清目标，不能默默写入旧的活动草稿。 |
| “把这张发票放到 BX…；删除第 2 张并重传” | 先解析草稿和稳定票据 ID；有歧义时不上传/删除。删除前展示文件名、单号并要求一次性确认；新文件上传成功前不自动删除旧文件。 |
| “这张还缺什么/进度如何” | 从 Go 校验、票据/OCR、员工可见复核进度与单据状态生成可执行说明；没有审批/付款来源时如实说明。 |

搜索字段第一期包含 `status`（仅 Go 支持的状态）、创建日期区间、事由关键词、费用类别、申请报销金额范围；精确单号继续走专用本人查询。支持创建时间、申请金额的升降序，稳定次序以 `id` 补齐。自然日期按产品配置的业务时区解释，本机默认为 `Asia/Shanghai`，回显实际区间。金额筛选始终指申请报销总额，OCR 票据金额不能混用；未填写金额不落入金额区间。无效或矛盾条件要澄清，不静默丢弃条件。

员工可要求 1–100 条结果；默认展示 5 条。飞书单条回复最多展示 10 条且受现有 1000 字限制，Web 对话可展示更多；请求 30 条时保存剩余数量与游标，逐页展示至 30 条或结果耗尽。超过 100 条则提示缩小范围或继续分页，不一次输出巨大消息。总数由 Go 对相同条件计算并标注“查询时匹配”，数据变化后下一页可更新，不把旧总数当实时保证。

## 查询和目标状态

在 Agent 会话中持久化经服务端校验的 `searchState`（规范化筛选、排序、游标、剩余请求数、最近展示页的序号到 Go ID/单号映射、生成时间）、`selectedReadClaimId` 和单独的 `selectedEditClaimId`。仅保存 Go ID 与必要的版本/有效期信息，不创建跨库外键，也不把完整结果列表放入模型上下文。搜索状态可供“下一页/再看 10 条”和“第二张”使用，过期或用户发起不同搜索时清除；翻页不得意外切换办理目标。

明确单号或列表序号都必须由服务端对最新本人搜索结果解析为稳定 Go ID；“第二张”只能引用尚有效的那一页，不引用聊天摘要中的历史文字。选中只读单据不赋予编辑资格。显式选中办理目标时重新从 Go 验证本人和 `DRAFT`，保存独立办理指向，显示“当前正在办理：单号”。切换目标不会改动或丢弃原活动 Intake；新建 Intake 时清除旧只读/办理选择。办理目标在每次写操作前再次由 Go 验证，不能仅靠会话缓存判定权限或草稿状态。

有已选只读目标与不同办理目标、或已有活动 Intake 与指定旧单并存时，任何“这张/这个”写入或提交请求只要目标不唯一，必须澄清并复述单号。显式单号的一次性操作可直接确定目标；无显式单号时只在唯一明确的办理目标上操作。模型不能凭“最近一张”“应该是那张”猜测写目标。查询上下文和办理上下文分别显示，用户可以明确“回到当前草稿”或“切换办理 BX…”。

提交准备/确认从现有 Intake 专属 Token 扩展为绑定会话、员工、目标 Go claim ID、版本、金额摘要和过期时间的持久待确认动作。选中既有草稿也可以按原有 Go 提交两阶段流程提交；更换办理目标、改字段、增删票据或 Go 版本变化均清除旧确认。精确“确认提交”只能消费当前尚有效的待确认动作，不由模型自由判定。

## Go API、工具及领域边界

1. 扩展 `GET /api/v1/claims` 或增加 `/api/v1/claims/search`，使用类型化 `status`、日期、关键词、费用类别、金额上下界、排序、`limit`、不透明游标；返回 `{items, totalCount, nextCursor}`。始终由认证上下文决定 `owner_id`，不接受模型提供的员工 ID。数据库执行过滤、稳定排序及游标分页；精确 `claimNumber` 语义保持不变。索引按实际查询计划添加，禁止在 Agent/Node 端进行不完整筛选。
2. Agent 新增 `search_owned_claims`、`get_owned_claim_progress`、`delete_owned_receipt`、`delete_owned_draft` 等类型化工具；已有本人查单、工作台读取、字段 PATCH、上传、校验和提交工具继续复用。工具网关校验字段白名单、数量上下限、游标和动作参数，并记录调用结果；Go 对每次领域动作再次校验本人、草稿状态、版本和幂等键。
3. Agent 对话可写字段仍限 `purpose`、`expenseCategory`、`participants`、`projectCode`。金额、币种、备注及票据 OCR 字段的人工修正只由现有 Web/财务复核流程负责；Agent 对这些请求返回目标单据的精确工作台链接，不声称已修改。所有写入均按 Go 版本 PATCH，回读一致后才回复“已保存”，并清除旧提交确认。
4. 票据管理以 Go `receiptId` 为准：读取带状态和文件名的本人票据列表；上传须先确定唯一草稿目标；删除须确认单号和票据并使用一次性、有时限的待确认动作，再调用已有 Go 删除接口。确认时重新验证票据仍属于该草稿并为可删状态。替换先上传新文件，不自动清除旧文件；上传/删除影响校验与 OCR 建议金额时由 Go 重算。
5. 草稿删除通过新的 Go 本人 `DELETE /api/v1/claims/{id}` 暴露已有领域删除能力，要求显式选中单号、版本和一次性确认；已提交单不可删除。Go 负责数据库删除、审计/事件及附件对象的可靠清理或排队清理。若清理失败，要有可重试状态，不能回复“全部删除成功”。会话同时清除指向已删除单据的读/办目标和确认动作。
6. 进度读取组合 Go 单据状态、提交记录、票据/OCR 状态、校验问题和员工可见的人工复核投影；新增员工安全的只读活动/复核摘要接口，不能暴露财务内部意见或其他员工信息。缺项说明必须来自 Go 校验及当前记录，Agent 只把阻断项映射为“可在对话补充”或“请到该单 Web 页面操作”。为未来审批/付款预留版本化阶段扩展字段及事件消费者接口，但本期值为空或 `NOT_CONNECTED`，不能生成假的进行中、已批准或已付款文案。
7. 复用现有 Go Outbox/NATS 与 Agent 投递去重机制，按本人对 OCR 失败/完成、需要复核/复核结果、提交完成发送必要的私聊通知；用户主动询问时始终重新读取 Go 当前值，不以通知文本为事实源。跨渠道同一员工身份、消息重投和工具重试必须幂等。

React 工作台继续直接读写 Go；本期不强制加入 Agent 悬浮入口。查询与进度的新 Go 合同同步 OpenAPI/类型及 Web 列表，至少保证 Web 能显示并打开 Agent 返回的单号与状态。飞书链接须使用当前配置的有效公开地址；无可用地址时回复单号，不输出失效的固定示例域名。

## 失败、隐私和可观察性

- 飞书群聊仅可问非敏感政策/一般帮助；列表、详情、选单、附件、改字段、删除和提交一律引导私聊。不存在或无权限的单据统一为不泄露存在性的回复。
- 401/403/404、版本冲突、非草稿、校验阻断、游标过期、消息重放及 Go 服务不可用各有可恢复文案；失败不得回退到旧 Prisma 报销写路径。已失败的动作不能在会话里留下“成功”或有效确认。
- 查询动作只读，不因模型错误触发修改；删除、提交须有明确目标和确认，确认 Token 绑定动作/员工/单号/版本/有效期，其他文本不能消费。所有领域写入保留 Go 审计和 Outbox；Agent 工具账本用于去重和链路追踪，日志不记录票据正文、完整消息、密钥或参与人员明文。

## 验收标准

1. 本人“上月草稿 12 张”“金额 100–500 元的单据有几张”等查询返回 Go 实际筛选结果、正确总数和稳定分页；旧单不因前 100 条截断而漏查。无效条件不会退化为无条件列表。不同员工、群聊均不能看到这些结果。
2. 查询 A、办理 B 并存时，“改这张”会澄清，绝不暗写 A 或 B；明确“编辑 A”且 A 为本人草稿后，字段、上传、删除和提交只影响 A。已提交 A 只读。原 Intake 草稿 B 仍可明确切回。
3. 飞书发票附在明确选中的草稿；附件歧义、重复文件名、OCR 中或待复核时准确显示状态。删除必须确认稳定票据 ID，重复消息仅删除一次；上传新文件失败不能丢失旧票据。
4. 指定旧草稿的提交使用 Go 最新金额/版本与校验；切换目标或修改后旧 Token 失效。未明确“确认提交”、过期确认、Web 并发修改、越权单号和非草稿都不会提交或显示成功。
5. “这张还缺什么/进度如何”可指出真实的校验阻断、OCR/复核及提交进度，给出对话可办动作或该单 Web 链接；审批/付款未接入时明确说明。事件重投不会重复通知。
6. 草稿删除只对本人草稿生效，需单号/版本/确认，附件清理失败可重试；Web 与 Agent 回读一致，审计可追溯。
7. Go API/仓储、OpenAPI、Agent 模型解析、工具网关、会话状态、Web/飞书私聊与群聊、幂等和双员工越权均有针对性测试；人工验收至少覆盖一个超过 100 单的员工、一个无权限员工和一个与当前 Intake 并存的旧草稿。
