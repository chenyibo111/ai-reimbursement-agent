# 飞书与 Web 同权的报销查询、摘要和确认提交设计

## 背景与意图

当前飞书机器人与 Web Agent 都通过 Go 报销工具网关办理报销；普通 React Web 工作台直接调用同一 Go 报销 API。飞书 `open_id` 与 Web 飞书登录映射到同一员工 ID，Go 报销数据按员工归属校验。

现有会话模型只能返回 `ANSWER`、`COLLECT_FIELDS`、`REQUEST_SUBMISSION` 等粗粒度动作。它没有“读取当前单据/票据金额”的动作，能在未调用 Go 的情况下自行解释“无权限”；而 `REQUEST_SUBMISSION` 把只读摘要和申请提交确认令牌混在一起。用户问“发票多少钱”或“生成提交摘要”时，可能得到无依据的回答；再发送“确认提交”会因 Intake 未进入 `READY_TO_SUBMIT` 而被拒绝。

目标是让飞书私聊员工与 Web 对同一报销单具有相同的本人读取和提交能力。模型只识别意图与有限字段；金额、状态、提交条件和授权结论来自 Go API，最终提交始终需要用户针对当前单据和版本的明确确认。

## 已选方案与取舍

### 方案 A：固定关键词路由

为金额、摘要和提交分别增加规则匹配。改动较小，但“这张票多少钱”“我要报销多少”“可不可以交了”等同义问法容易漏判，也与已有的模型意图识别方向不符；不采用。

### 方案 B：结构化模型意图 + 确定性 Go 工具执行（已选）

扩展模型的结构化动作集合；服务端检查动作、当前 Intake、身份和参数，再调用现有 Go 工具网关。模型不生成金额或权限结论。读数据、只读摘要、申请确认令牌和最终提交是四个独立阶段。继续沿用已完成的 Go 工具网关硬切换，不引入 Prisma 报销领域兜底。

代价是需要更新会话动作契约、Go 工具返回类型、两端入口和测试，但可保持同义问法能力以及对写操作的确定性控制。

### 方案 C：让模型自由选择并直接调用任意工具

自由度更高，但难以证明提交意图、字段边界及确认过程，尤其不适合财务写操作；不采用。

## 范围与非目标

纳入飞书私聊和 Web Agent 的当前报销单查询、单张/多张票据金额查询、只读摘要、提交准备与确认提交；更新 Agent Go 端口契约、工具适配、会话状态和安全回复；覆盖权限、并发修改、幂等与同义问法测试。

普通 React Web 表单、Go 报销规则、OCR 算法和审批流程不在本次改造范围内。现有 Go 单据尚未完整提供费用归属与审批信息时，Agent 必须明确说“当前系统没有可确认的数据/字段”，不得依据政策文档或会话历史编造。权限“与 Web 一致”指同一员工读取本人数据、满足相同 Go 提交校验，而非让飞书消息绕过 Go API。

## 身份与安全边界

1. 飞书入站消息须经既有消息真实性校验，以发送者 `open_id` 映射并同步员工 ID；Web 使用登录会话映射的同一员工 ID。客户端或模型提供的员工 ID、角色、单据归属声明一律不可信。
2. Agent 使用签名 JWT 与服务密钥调用 Go；Go 在读取单据、读取票据、申请确认和提交时继续按活动员工与单据归属校验。不同员工即使猜出 `claimId` 也不能读取金额或提交。
3. 金额、单据状态和提交确认属于敏感操作。作为本设计的安全默认值，飞书**私聊**可执行；群聊即使 `@机器人`，也不在群中回显金额、单据摘要或提交结果，应提示员工转到私聊或 Web。若产品确需群内展示，须另行明确授权与隐私设计。
4. `source_channel` 可继续用于审计和链路定位；不得把“飞书平台 OAuth scope 不包含报销字段”误判成自有 Go 报销服务的授权结果。模型不得自行宣称“有/无权限”。

“当前单据”只指该员工在**当前会话的 Intake** 中绑定的 `claimId`，不由模型猜测，也不自动挑选列表里最新的草稿。当前会话未绑定单据时，请员工先开始报销并上传票据，或去 Web 工作台查看已有单据。通过报销单号选择其他历史单据可后续扩展，但不属于本期；这不改变 Go 对本人单据的授权范围。

## 会话动作与数据流

```text
员工消息（Web 私聊 / 飞书私聊）
  -> 身份解析 + 当前 Intake
  -> 模型输出结构化意图（不是业务事实）
  -> 服务端校验动作与当前 claimId
  -> Go Tool Gateway 读取/校验/申请确认/提交
  -> 服务端按 Go 返回值生成可核对的回复
```

建议的高层动作：`READ_CLAIM`、`READ_RECEIPT_AMOUNT`、`READ_SUBMISSION_SUMMARY`、`PREPARE_SUBMISSION`，保留 `COLLECT_FIELDS`、政策问答和普通回复。最终“确认提交”继续由服务端在已准备状态下识别，不交给模型自由决定。解析结果必须通过严格 schema 校验；未知或无效动作只能请求澄清，不能回退为“猜测的事实性回答”。普通 `ANSWER` 的模型自由文本不得直接作为单据事实回复：服务端只允许它处理问候、操作引导等非业务事实，涉及当前单据/金额/权限时必须转为读取动作或提示澄清。

- **查询金额**：使用 `get_claim_workbench` 读取本人当前单据及票据。扩展 Agent `ClaimSnapshot` 和 `ReceiptSnapshot` 以容纳 Go 已返回的 `requestedAmountCent`、票据 `totalAmountCent`、识别状态等必要字段。回复明确区分“申请报销总额”“OCR 发票价税合计”“票据金额之和”，不把其中一个冒充另一个。单票据可直接回答；多票据且“当前发票”不明确时列出可区分的票据及金额，或请求员工指定。金额为 `null`、仍识别中或待复核时如实标识，绝不填零或引用历史聊天当现值。
- **只读提交摘要**：读取当前 Go 单据、票据和 `get_claim_validation`；即使存在阻断项，也展示已确认事实与待补/待复核项。该动作不申请确认令牌、不改变单据和 Intake 状态。若 Go 暂不可用，返回“暂时无法查询”，不能解释成“无权限”。
- **准备提交**：员工表达明确提交意图时，先以最新 Go 数据和校验结果生成确认内容，再调用 `request_submission_confirmation` 获取绑定员工、单据和当前版本的确认令牌。只有 Go 返回成功才将 Intake 置为 `READY_TO_SUBMIT`，并回复金额、事由、票据数和“确认提交”的下一步。阻断项应逐项展示；不能把只读摘要误当成可提交状态。
- **确认提交**：仅在同一员工、同一会话的 `READY_TO_SUBMIT` 中使用保存的令牌调用 `submit_claim`。Go 再校验单据版本及提交条件，幂等键与工具调用账本防止消息重投重复提交。成功后保存提交编号并使 Intake 终结；状态缺失、令牌过期或单据已修改时给出明确重新准备的指引，而不是通用操作失败。

任何对事由或票据的变更都会使现有提交准备失效；Go 的单据版本检查是最终防线。Web 表单和飞书会话可改动同一单据，所以确认前不能只信会话缓存的金额或版本。会话历史与政策引用只帮助理解意图，不是金额、状态和授权的事实源。

工具数据契约以 Go 现有 `GET /api/v1/claims/{claimId}`、`GET /api/v1/claims/{claimId}/receipts` 和 `GET /api/v1/claims/{claimId}/validation` 为准：单据至少读取 ID、版本、状态、事由、`requestedAmountCent`、`totalAmountCent`、币种和票据数；票据至少读取 ID、原始文件名、状态、发票号码、`totalAmountCent` 和识别置信度。Go 已返回但 Agent 端口未声明的字段要补入类型；若 Go 实际未返回必需字段，则实施阶段扩展 Go API 契约，绝不能以会话历史填补。金额单位统一为分，输出时按币种格式化；本期仍只支持 CNY。

## 用户可见回复原则

- 问“当前发票金额是多少”：按当前 Go 票据返回“发票号码/文件名、价税合计、识别或复核状态”；没有可信金额则说尚未识别/待确认，并给工作台链接。
- 问“申请报销总额是多少”：返回当前单据的申请总额及币种；未填写时明确未填写，不用 OCR 合计冒充申请额。
- 问“生成提交摘要”：返回只读事实和阻断项；不声称已经提交，也不引导立刻“确认提交”，除非员工随后明确发起提交准备且 Go 成功返回令牌。
- 发送“确认提交”但没有有效准备：说明尚未生成有效提交确认，并引导先核对摘要/发起提交；不产生写操作。
- Go 返回 401/403/404、校验阻断、版本冲突或 5xx 时分别使用准确的安全文案；对“单据不存在”和“无权访问”统一给不泄露存在性的提示。以现有 HTTP 状态与标准错误码为基础做显式映射，未知错误只称服务暂不可用并记录内部诊断；不把服务不可用、缺字段或模型没调工具说成权限限制。

## 验收与回归

1. 同一员工在飞书私聊和 Web 查询同一单据时，申请总额、每张发票金额和状态一致；飞书入站身份与 Web 身份落在同一员工 ID。
2. 另一个员工通过飞书私聊询问或试图提交该 `claimId`，Go 拒绝，机器人不泄露金额或单据存在性。群聊不输出敏感数据或执行提交。
3. 覆盖“发票多少钱”“这张票价税合计”“我要报销多少”等同义问法；单张、多张、缺金额、OCR 中、待复核均有可核对的回复。
4. “生成提交摘要”在未满足提交条件时仍可返回只读事实和阻断项，且不产生确认令牌；“准备提交”只有校验通过才生成令牌。
5. 未准备直接“确认提交”、准备后修改单据、令牌失效、重复投递同一飞书消息均不会错误提交或重复提交；成功提交的编号与 React Web 列表一致。
6. 用模型返回 `ANSWER`、错误动作、虚构金额/权限说明的测试样例证明服务端不会把模型文本当作金融事实直接输出。

## 待实施计划决定的细节

实现时可决定具体动作命名、回复模板组织、结构化模型 schema 和测试文件布局；必须保持上述读取/准备/确认边界及 Go 为唯一报销事实源。此设计不要求新增模型供应商、MCP 服务或独立数据库表；若现有 Go 确认令牌未满足员工/单据/版本绑定，则实施计划必须先补足 Go 侧校验。
