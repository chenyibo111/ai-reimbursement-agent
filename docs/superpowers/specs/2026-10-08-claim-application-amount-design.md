# 报销单申请金额、币种与备注设计

**日期：** 2026-10-08  
**状态：** 已确认，待实施计划  
**范围：** React + Go 迁移 Profile 下的员工报销工作台与报销单 API

## 背景与目标

当前工作台只允许创建草稿和上传票据。票据 OCR 会产生“已识别票据金额合计”，但报销单没有可由员工填写、核对并提交的申请报销总额、币种和备注。

本次为报销单增加三个独立字段：

- `requestedAmountCent`：员工申请报销总额，以分为单位保存；
- `currency`：ISO 4217 三字母币种代码，第一版固定为 `CNY`；
- `remark`：员工备注。

申请金额不是 OCR 票据汇总的替代字段。OCR 汇总仍是可审计的票据事实，申请金额是员工的声明；两者并列展示并供员工核对。

## 已确认业务规则

1. 新草稿的币种固定初始化为 `CNY`，前端展示“人民币（CNY，暂仅支持）”。字段按 ISO 代码存储，为后续多币种、汇率和按票据币种核验预留边界。
2. 没有可计入的 OCR 金额时，申请金额为空，不显示或写入 `￥0.00`。
3. 一份或多份票据识别完成后，若员工尚未编辑申请金额，系统将申请金额更新为已识别票据金额之和，来源标记为 `OCR_SUGGESTED`。
4. 员工保存过金额后，来源变为 `MANUAL`；后续上传、重识别、删除或 OCR 回填均不得覆盖该金额。
5. 员工可清空手填金额以恢复“采用 OCR 建议”的模式；下一个有效 OCR 汇总立即作为申请金额建议值。若没有识别金额，申请金额保持为空。
6. 草稿状态可编辑；已提交报销单不可修改。每次字段更新使用现有乐观版本号并产生新的草稿版本。
7. 金额输入只接受大于等于零、最多两位小数的十进制数；服务端将其精确换算为整数分，不接受浮点值或超出 `int64` 的金额。
8. 提交确认与最终提交读取同一份最新草稿。提交快照必须包含申请金额、币种、备注、金额来源和提交时的 OCR 汇总，保证后续票据或政策变化不改变历史事实。

## 数据模型与迁移

在 `reimbursement.claims` 增加：

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `requested_amount_cent` | `BIGINT` | 可空，非空时 `>= 0` | 员工申请金额 |
| `currency` | `CHAR(3)` | 非空，默认 `CNY`，第一版仅允许 `CNY` | 币种代码 |
| `requested_amount_source` | `TEXT` | 非空，默认 `OCR_SUGGESTED` | `OCR_SUGGESTED` 或 `MANUAL` |
| `remark` | `TEXT` | 可空，最长 1,000 个 Unicode 字符 | 申请备注 |

历史草稿以 `requested_amount_cent = NULL`、`currency = CNY`、`requested_amount_source = OCR_SUGGESTED`、`remark = NULL` 回填。迁移不从旧票据批量回写申请金额：只有后续发生 OCR 汇总刷新，或员工主动保存草稿字段时，才生成建议值，避免历史数据被静默改写。

## API 与领域边界

- `Claim` 读模型、Go domain `Claim`、OpenAPI 和 React 的生成类型均返回上述字段，金额保留为整数分。
- 既有 `PATCH /api/v1/claims/{claimId}` 扩展为原子更新：`requestedAmountCent`、`currency`、`remark`。请求必须携带当前 `version`，且只在 `DRAFT` 状态可更新。
- 金额来源为服务端控制字段：员工保存非空金额会设为 `MANUAL`；员工发送显式“恢复 OCR 建议”的清空操作会设为 `OCR_SUGGESTED`。客户端不能伪造来源。
- 票据 OCR 持久化成功后，由同一服务端事务（或受版本保护的重试）重算 `EXTRACTED` 且金额非空票据的合计；仅当草稿来源为 `OCR_SUGGESTED` 时同步该合计。
- `currency` 第一版服务端仅接受 `CNY`。未来多币种改造必须另行设计汇率来源、结算币种、票据币种与跨币种聚合，不能仅放开前端选项。
- 提交前校验增加：申请金额必须已填写；保持现有票据识别、权限、政策与版本检查。申请金额与 OCR 汇总不强制相等，但确认摘要在不等时显示差额提示。

## 工作台交互

在“票据归档”和“提交前检查”之间新增“报销信息”面板：

1. 显示不可编辑的币种控件“人民币（CNY，暂仅支持）”。
2. 提供带 `￥` 视觉前缀的申请金额输入框，保留用户原始输入；下方显示“已识别票据合计”。
3. 当来源是 `OCR_SUGGESTED` 时，显示“已采用票据识别建议；修改后将不再自动更新”；当来源是 `MANUAL` 且与 OCR 汇总不一致时，显示非阻断的核对提示和“恢复 OCR 建议”按钮。
4. 提供备注文本域，最多 1,000 字，说明该备注会随提交快照保存。
5. 保存按钮遵循现有表单行为：保存期间禁用控件、成功后就地刷新草稿版本并给出页面内成功反馈；冲突或失败保留输入并显示可恢复错误。表单使用 `noValidate`、显式标签、就近错误文本和 `aria-invalid`。
6. 提交确认区展示申请金额、币种、OCR 汇总及备注摘要；未填写申请金额时给出可读阻断项，不能请求确认。

窄屏下金额、币种和备注依次纵向排列。金额差异、OCR 缺失、保存中和会话过期均保持页面布局稳定，不能让输入内容丢失。

## 异步与一致性

- OCR 处理、重新识别和票据删除都复用一个“刷新 OCR 建议金额”应用服务，禁止各 Worker 或 HTTP Handler 直接写字段。
- 该服务以 claim id 和当前版本读取草稿，在来源为 `OCR_SUGGESTED` 时更新汇总值并递增版本；若发生版本冲突，重新读取并只在仍是建议模式时重试一次。
- 人工修改金额与 OCR 回填并发时，人工修改优先：服务端 CAS 失败后重新读取到 `MANUAL` 即停止回写。
- 备注不进入 OCR、向量知识库、公开日志或飞书机器人消息；它只随经过授权的报销单和提交快照返回。

## 验收与测试

1. 数据库迁移可在已有报销草稿库上前向执行，并正确建立默认 `CNY` 与可空申请金额。
2. Go domain、HTTP 和 PostgreSQL 测试覆盖金额格式、边界值、草稿状态、乐观版本冲突、仅 CNY、备注长度及提交快照。
3. OCR 测试覆盖：第一张/后续已识别票据更新建议金额；人工金额永不被 OCR 覆盖；清空后可恢复建议。
4. React 单元/组件测试覆盖表单回显、两位小数校验、保存、服务端错误保留输入、金额差异提示和恢复建议。
5. 浏览器验收：新建草稿 → 上传两张票据 → OCR 回填申请金额 → 人工修改 → 再次 OCR 不覆盖 → 保存备注 → 提交确认摘要与申请金额一致。

## 非目标

- 不实现多币种选择、汇率、折算、票据币种识别或跨币种汇总。
- 不变更飞书 Agent 对话收集字段；本期仅实现 React + Go 报销工作台能力。
- 不追溯修改已提交快照或已提交报销单。
