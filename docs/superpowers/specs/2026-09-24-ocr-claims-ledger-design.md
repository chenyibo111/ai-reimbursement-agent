# 本地 OCR 与报销单查询：产品与技术设计

## 1. 目标与范围

本迭代解决三个员工可见问题：票据不能再由固定样例数据冒充识别结果；登录后默认进入自己的报销单；提交后的报销单可查询、可回看且不可修改。

范围包括：本地 PaddleOCR 服务、票据字段解析与澄清、报销单列表、已提交单据的不可变详情、30 天持久登录。范围不包括财务审批、发票验真、付款、ERP/OA 接入或第三方云 OCR。

## 2. 用户体验与路由

`/` 是受保护入口：已登录时重定向到 `/claims`，未登录时重定向到 `/api/auth/feishu/login`。飞书授权成功后同样进入 `/claims`。

`/claims` 是“我的报销单”列表。只显示当前员工的数据，默认按最近更新倒序，并提供：状态（全部、草稿、已提交）、提交日期范围、报销单号或报销事由关键词筛选。顶部主操作为“发起报销”，跳转 `/claims/new`。

草稿继续使用 `/claims/[claimId]` 工作台。已提交后，客户端以提交接口返回的单据编号跳转 `/claims/[claimId]/detail`；该详情页是只读的，包含编号、提交时间、报销事由、合计、提交快照中的费用明细、字段来源、原始识别结果摘要和校验记录。详情页不渲染上传、编辑、聊天、确认或提交控件。

列表、工作台与详情页都提供“我的报销单”导航入口。空列表说明尚无报销单并提供发起入口；筛选无结果提供清除筛选操作；服务端失败显示页内可恢复错误。

## 3. 身份与会话

会话 Cookie 保持 `HttpOnly`、`SameSite=Lax`，生产环境保持 `Secure`，不写入 Local Storage。会话令牌携带员工 ID、签发时间、过期时间和随机会话 ID，并以 `SESSION_SECRET` 签名；服务端拒绝过期、格式错误或签名无效的令牌。

Cookie 的 `Max-Age` 为 30 天。正常刷新和浏览器重启不触发飞书授权；显式退出清除 Cookie。认证成功、退出和认证失败都不能泄露飞书令牌或密钥。所有列表和详情 API 都以 Cookie 中的员工 ID 做归属过滤，客户端传入的员工 ID 一律忽略。

## 4. 本地 PaddleOCR 边界

新增 Docker 化 Python OCR 服务，只在 compose 私有网络暴露。它接收受信任的临时输入文件或文件字节与 MIME 类型，不持有数据库或 MinIO 凭据，不提供公网端口。

Web 服务仍是唯一可访问 MinIO 的组件：提取路由通过对象存储读取原始附件，再把受大小与页数限制的内容转发给 OCR 服务。图片直接识别；PDF 按页转为图像，合并文本块。OCR 服务返回逐页文本块、模型版本和模型置信度；它不负责业务字段判断或数据落库。

`PaddleReceiptExtractionProvider` 实现现有识别接口，负责把 OCR 文本规范化为内部字段：票据类型、发票号码、开票日期、价税合计、税额、销售方。字段解析使用可审计的确定性规则（标签邻近、金额/日期/票号格式校验），不会从无关文本猜测金额。每个字段的置信度取 OCR 置信度和规则匹配质量中的保守值。

无法解析的字段返回 `null` 和低置信度；字段有冲突或关键金额缺失时不创建可计入的费用明细，生成待补充项。原始 OCR 响应、已解析字段及 `paddleocr` 模型版本写入 `Receipt.extractionPayload` 和 `Receipt.extractionVersion`。识别服务故障将 Receipt 标为 `FAILED`、保留附件并给出可重试错误，不回退为固定样例数据。

本地环境以 `RECEIPT_EXTRACTION_PROVIDER=paddleocr` 启用。`fixture` 只允许测试环境使用；生产配置若为 fixture 必须在启动时失败。

## 5. 数据与 API 契约

保留 `ClaimDraft` 与 `SubmissionSnapshot` 模型。提交事务必须把报告详情所需的完整内容写入快照，包括编号、事由、总额、费用明细、字段来源、关联票据识别摘要和提交时间。详情 API 必须读 `SubmissionSnapshot.payload`，而非依赖可变草稿明细。

新增 API：

- `GET /api/claims`：返回当前员工的列表投影和筛选分页信息；不返回对象存储键或完整 OCR 文本。
- `GET /api/claims/[claimId]/detail`：仅当当前员工拥有且状态为 `SUBMITTED` 时返回不可变快照；草稿返回 404，非归属返回 403。
- `GET /api/auth/session`：返回当前登录员工的最小展示信息，未登录返回 401；仅用于受保护页面的会话恢复。

现有 `GET /api/claims/[claimId]` 继续服务草稿工作台。`POST /submit` 成功返回详情跳转所需的 `claimId` 和 `submissionNumber`；同一确认令牌不能重复生成报销单。对已提交草稿请求确认摘要应明确返回冲突，不再生成看似可提交的摘要。

## 6. 状态、错误与可访问性

识别状态为 `PENDING → EXTRACTING → EXTRACTED | FAILED`。界面在提取中显示进度；失败提供“重试识别”，不会删除附件或填入虚构值。低置信关键字段在工作台以明确标签、原值和编辑控件呈现，并在最终提交前阻断。

列表筛选控件使用语义化 label，状态和错误使用 `role=status` / `role=alert`。移动端将列表卡片化；桌面端使用可横向滚动的表格。详情页的编号、金额和字段来源可被键盘和屏幕阅读器读取。

## 7. 安全约束

附件继续经过签名、大小、页数和 ClamAV 校验后才可进入 OCR。OCR 结果与票据文本均为不可信输入，不能作为指令执行、身份判定或提交授权依据。日志不输出附件、OCR 全文、Cookie、会话令牌或密钥。

外部不存在 OCR 调用，因此票据不离开本机部署边界；但管理员仍需把 MinIO、PostgreSQL、OCR 服务限制在私有网络，并维护模型镜像与病毒库更新。

## 8. 验收与测试

- 使用伪造 OCR HTTP 服务验证字段映射、空字段、低置信度、OCR 故障和 fixture 生产禁用；不依赖真实票据内容测试解析。
- 以集成测试验证列表只返回所有者数据、筛选正确、详情仅返回提交快照、草稿详情 404、提交后重复请求 409。
- 以单元测试验证会话 30 天 Cookie 属性、令牌过期和签名拒绝。
- 以 Playwright 验证已登录刷新仍停留在列表、从列表创建草稿、提交后跳转详情、详情不能编辑，以及窄屏布局。
- 通过 Docker Compose 拉起 OCR、MinIO、ClamAV、PostgreSQL 后，用一份脱敏票据进行人工冒烟；识别结果必须来自 OCR 服务而非 `FIXTURE-INVOICE`。

## 9. 交付顺序

先建立会话和报销单查询 API/数据快照，再交付列表与只读详情，以修复当前可见路径；随后接入 OCR 服务和 Provider，最后完成真实票据冒烟、全量测试与文档更新。每一阶段独立可回归，且不改变已提交快照的历史内容。
