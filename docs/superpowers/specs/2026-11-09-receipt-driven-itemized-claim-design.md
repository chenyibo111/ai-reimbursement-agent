# 票据驱动的费用明细与智能补单设计

**状态：用户已确认（2026-11-09）**

## 2026-11-11 交互修订

票据识别结果和费用明细在 Web 中只读展示票据类型、金额及识别状态。申请报销信息显示整单报销事由和所有已识别费用类别的汇总；正常视图不展开逐票编辑。草稿员工可以通过“更正分类或补充信息”入口，按具体票据修改类别、通用事由、项目编码和同行人；OCR 金额不在该入口编辑。服务端仍保留一票一明细与逐条政策校验，不能把整单类别广播到各票据。模型有票面证据表明票据不属于打车、餐饮、住宿、交通时，分类为 `OTHER`，默认类别“其他”、通用事由“其他费用”；已发布类别规则不允许“其他”时正式类别留空，低置信或无证据时仍为 `UNKNOWN`。本节覆盖下文关于 Web 逐票常显可编辑字段与仅四种类型的旧描述。

## 意图与验收目标

员工从 Web 或飞书 Agent 上传打车、餐饮、住宿、交通等票据后，OCR 完成即自动在同一张报销草稿中生成可编辑的费用明细。每张票据对应一条明细，保留票据类型、费用类别、金额、通用事由及其来源。混合票据仍属于一张报销单；整单展示所有类别、概括性事由和金额合计。用户在 Web 核对、修改并按现有确认流程提交；Agent 读取同一份 Go 数据并在私聊中反馈识别结果和待补字段。

票据能够证明的事实才预填。打车票可以给出“市内出行打车费”这类通用事由，但不能据此编造客户拜访、项目编码或同行人。模型输出是建议，不能成为授权、票据真实性或政策通过的依据。

## 已确认的选择与备选方案

- **采用每票据一条费用明细、整单汇总。** 可以分别表示打车和餐饮，按各明细类别执行政策校验，支持后续逐条纠错。代价是 Go 数据结构、API、Web 和 Agent 均需扩展。
- 未采用把“交通费、餐饮费”写入现有 `expenseCategory` 文本字段：当前 `CATEGORY_ALLOWED` 精确比较单一类别，混合字符串会使规则失真，也无法对应每张票据。
- 未采用仅在 Agent 对话中保存分类结果：Web 上传和飞书上传必须获得相同的持久化结果，Go 仍是单据的真实来源。

## 现状与边界

Go OCR 目前从识别文本中解析发票号、日期、金额、销售方及整体置信度，未把票面文字或票据类型传给后续补单。金额会对已识别票据求和，但申请单仍只有单值 `expense_category`；`CATEGORY_ALLOWED` 和 `CATEGORY_REQUIRED_FIELD` 也按整单类别执行。Web 表单有事由、类别、项目编码、同行人、申请金额、备注；Agent 的字段写入端口目前仅允许前四项，金额和备注不能由 Agent 写入。

本设计扩展 Go 主业务链路。已退役的旧 Node 票据链路中存在 `receiptType` 字段，但不作为新明细的事实来源。沿用员工归属校验、草稿版本、工具审计、提交确认令牌与票据复核状态。

## 数据与接口

1. 新增 `expense_items`，每条以 `receipt_id` 唯一关联一张票据，包含 `claim_id`、票据类型、费用类别、金额分、通用事由、项目编码、同行人及各建议字段的来源/确认状态。票据号、开票日期和销售方仍保存在票据实体，不复制为另一份可编辑事实。项目编码、同行人等无法推断的字段为 `null` 或空集合，不由模型填充默认值。
2. OCR 结果扩展为受长度限制的票面文字及解析字段，供受控分类步骤使用。票面文字仅进入受限的识别存储和模型请求；日志、工具审计、飞书消息不记录全文。记录 OCR/分类模型版本和结果来源，便于追溯与重算。原始票据文件继续走现有对象存储与权限边界。
3. 分类器接收 OCR 文本、已经解析出的金额等事实、当前可用的费用类别，以及严格的结构化输出约束。输出 `receiptType`、候选 `expenseCategory`、通用 `purpose`、可选备注信息、证据片段/位置、字段置信标记和 `unknown`。金额由 OCR 解析和现有校验链路决定；模型不能凭空生成或修改金额。类别先映射到已发布的允许类别；配置了允许类别而无法可靠匹配时留空并提示用户选择。未配置类别规则时使用服务端受控的类别映射，模型自由文本不能直接作为正式类别。
4. Go 以同一员工权限返回 `expenseItems` 和整单汇总。单值 `expenseCategory` 为旧接口兼容字段：仅当明细都属于同一类别时返回该值，混合类别时为空；新增 `expenseCategories` 列表供 Web/Agent 展示与搜索。新增按版本更新单条明细的接口，只有草稿所有者能修改；重复请求和 OCR 重试不能生成重复明细。提交快照固定每条明细及对应票据。新明细草稿的整单 `expenseCategory`、`projectCode`、`participants` 只作为兼容读取值，不接受旧 PATCH 写入；Web 改为逐条编辑，Agent 增加指定票据/明细的受控写入工具，目标不明确时先要求用户指定。无明细的旧草稿继续支持旧 PATCH；不能把旧整单字段偷偷广播到所有明细。
5. 整单金额默认合计有效明细的当前金额（包括用户纠正后的明细金额）；保留现有手工填写整单总额的优先级，并显示与明细合计的差额。差额不新增提交阻断，因为现有流程允许手工申请金额与 OCR 合计不同，部分报销可能是合理需求；提交确认摘要须明确显示申请金额、明细合计及差额，由用户显式确认。整单事由默认由明细通用事由去重概括，例如“市内出行及餐饮费用”；用户修改后不再被自动重写。整单备注只在票面有可用信息时建议，不将模型猜测写成事实。

## 上传后的状态与用户操作

1. Web 和飞书上传均走同一条票据上传、OCR、分类、明细持久化流程。OCR 进行中显示“待识别”；成功后自动预填草稿，并通过现有事件/查询机制刷新 Web，Agent 在私聊给出各票据分类、金额、合计和仍需补充的字段。模型失败不能阻断票据保存：保留 OCR 事实与金额，类别/事由留空并提示人工完成。
2. Web 以票据为单位展示明细，标明“票据识别”“AI 建议”“人工填写”，支持纠正类别、金额、通用事由及可选字段。明细可定位对应票据预览；汇总区显示所有类别及金额合计。编辑单条明细不应要求重新上传票据。
3. 用户手工修改的字段具有优先权。后续 OCR 重试、分类重试或新增票据只更新未被手工修改的建议字段，不覆盖已确认字段。新增或删除票据时只增删对应明细，并重算自动来源的汇总；提交确认令牌随任何影响提交内容的修改失效。
4. 低置信、重复或待财务复核的票据继续走现有复核流程；可以展示受限的建议，但不能作为可提交的有效金额或绕过原有阻断。票据文字视为不可信输入，不能让其中的指令改变模型职责、工具权限或系统策略。

## 政策校验与兼容

`CLAIM_TOTAL_MAX` 仍针对整单申请金额；`CATEGORY_ALLOWED` 对每条有效明细的类别分别校验；`CATEGORY_REQUIRED_FIELD` 对命中该类别的明细检查项目编码/同行人，错误定位到明细和票据。发布规则与知识库问答仍是两套机制，不因模型分类就宣称政策已通过，也不调整既有政策检索门槛。提交前保持 Go 的基础校验、票据状态校验、政策校验和显式确认。

已有已提交单据和快照保持原样。已有草稿及票据以兼容迁移生成明细：金额可采用已保存的 OCR 事实，无法从旧数据可靠推断的类型和类别留空；不在迁移中调用模型或伪造业务事由。迁移期间旧字段继续可读，且针对无明细的旧单据保留原有校验路径。只有确认完成数据回填与调用方切换后，才考虑移除旧字段或旧写入路径。

## 分阶段交付

1. **明细基础与 Web 核对。** 增加数据库明细、Go API、逐条类别政策校验和提交快照；Web 能显示、编辑每张票据的明细与整单汇总。先用现有 OCR 金额生成明细，类型、类别和事由无可靠依据时留空，由用户填写。迁移旧草稿并验证旧提交单据仍可读。本阶段不宣称已经完成 AI 分类；新链路在端到端校验通过前用发布开关控制，旧链路继续服务现有单据。
2. **智能分类与自动预填。** 扩展 OCR 结果，加入受控模型结构化分类和类别映射。Web 或飞书上传都走同一服务端流程；识别完成后自动补全可推断字段，混合票据生成多条明细。覆盖模型失败、低置信、重复事件、人工覆盖和金额重算。上线前用脱敏的打车、餐饮、住宿、交通及模糊票据样本评估分类质量。
3. **Agent 对话补单。** Agent 读取 Go 明细和汇总，在私聊报告识别结果、待补字段和工作台入口；新增指定明细的受控修改工具，保持本人权限、版本校验、工具审计与提交确认。群聊仍不暴露个人单据。验证 Web 与飞书看到相同数据，纠错在两端一致。
4. **灰度与验收。** 先对少量测试员工启用新链路，逐步覆盖旧草稿及真实票据；观察分类错误、人工纠正率、模型失败和提交阻断原因。每阶段需通过相关回归与数据一致性检查再扩大范围。数据库新增结构保持向后兼容，回退发布开关时不删除明细或覆盖已提交快照。

## 验收与风险验证

- 单张打车、餐饮、住宿及交通票分别生成正确的票据类型、允许的类别、OCR 金额和通用事由；项目编码、同行人等没有证据时保持空白。
- 一张草稿含打车和餐饮票时有两条对应明细、两个类别、正确金额合计和概括性事由；Web 与 Agent 查询结果一致。
- 模型未知类别、无效结构化输出、超时、OCR 低置信、重复票、缺失金额均有明确的人工处理状态；不能默默填入猜测值或误报“已完成”。
- 重复上传事件、OCR 重试、并发新增票据不会产生重复明细或覆盖人工修改；版本冲突按现有规则回读与提示。
- 类别规则对混合明细逐条生效，整单上限仍按合计生效；修改明细后旧提交确认失效，提交快照包含所有明细。
- 新明细草稿拒绝旧整单类别/项目/同行人 PATCH 并给出可操作的错误；旧草稿兼容写入不回填到明细。手填申请金额与明细合计不同时，确认摘要展示差额，仍可按现有规则提交。
- 使用两个员工账号验证跨用户读取/修改被拒绝；校验模型提示注入、敏感票面内容不入日志。回归 Web 上传、飞书上传、财务复核、旧草稿、旧提交记录。

## 留给实施阶段的技术选择

具体数据库字段名、API 路由、受控类别映射与模型提示词由实施阶段按现有规范确定；需在实现计划中先列出数据库迁移、Go 服务、Web 表单、Agent 工具和端到端验收的顺序。分类质量应使用覆盖上述类型及模糊票据的真实脱敏样本评估，不能仅凭模型格式正确判断成功。
