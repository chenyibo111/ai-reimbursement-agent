# 中国单企业 AI 报销 Agent：产品与技术设计

## 1. 背景与目标

为一家中国企业提供独立的报销 Web。员工通过对话式界面上传发票或其他报销凭证，系统自动提取可确定的票据字段，向员工澄清无法确定的业务信息，最终由员工确认并提交报销单。

首期的目标是缩短填单时间、减少漏填，并保留完整的可审计链路；不是取代财务审核，也不是让模型自主决定报销结果。

### 成功标准

- 员工可完成“上传票据—补充信息—确认—提交”的闭环。
- 已识别字段自动填充，低置信度或异常字段清晰提示。
- 所有提交均由员工显式确认，且可追溯到原始票据、识别结果和字段修改。
- 后续可接入飞书机器人，但 Web 与飞书复用同一个报销 Agent 和草稿数据。

## 2. 范围

### 首期包含

- 单企业、员工自助使用的独立 Web。
- 对话式上传图片或 PDF，并支持一张报销单附多张票据。
- 票据结构化识别、字段置信度、手工修正和最少必要澄清。
- 报销草稿、规则校验、确认摘要和“已提交”报销单。
- 附件安全、基础重复票检测、审计日志。

### 首期不包含

- 财务审核、审批流、付款和 ERP/OA 对接。
- 多企业租户管理、计费和复杂的多租户运营后台。
- 在飞书内编辑复杂报销明细或完成最终提交。
- 以模型判断票据真伪或自动批准报销。

## 3. 总体架构

采用“报销 Agent 核心 + 渠道适配层”的模块化单体。Web 是首个渠道；飞书机器人后续只新增适配层，不复制业务逻辑。

```text
Web 对话框 / 飞书机器人
          ↓
      渠道适配层
          ↓
  API、身份与会话服务
          ↓
       报销 Agent
          ↓
        工具网关
   ┌──────┼──────┐
票据识别  规则校验  报销单服务
   ↓        ↓        ↓
对象存储、关系数据库、异步任务、审计日志
```

耗时的文件处理和识别放在异步任务中；用户界面通过轮询或推送获得“识别中、待补充、待确认”等进度。首期不拆分微服务，但模块间应通过清晰接口隔离。

## 4. 用户流程与状态

1. 员工创建草稿，并输入或后续补充报销事由。
2. 员工在 Web 对话框上传一个或多个图片/PDF 附件。
3. 系统安全处理文件并异步识别票据，返回票据类型、结构化字段和置信度。
4. 规则服务检查必填项、重复票、日期与金额异常等；Agent 按阻断程度发起最少必要的澄清。
5. 员工通过对话回答或在结构化明细页编辑字段。
6. 系统展示票据明细、合计金额、异常处理结果和不可变确认摘要。
7. 员工显式确认；服务端再次校验成功后生成报销单编号，保存提交快照。

状态为：`草稿 → 识别中 → 待补充 → 待确认 → 已提交`。识别失败或校验失败时保留草稿和原始附件，不丢失用户进度。

## 5. Agent 与工具边界

Agent 只负责理解用户意图、编排流程和生成澄清话术；它不能绕过服务端规则修改关键事实或直接提交。

| 工具 | 职责 | 约束 |
|---|---|---|
| `create_claim_draft` | 创建或恢复草稿 | 仅当前员工可访问 |
| `attach_receipt` | 将附件挂到草稿 | 校验文件安全与归属 |
| `extract_receipt` | 发起或读取票据识别 | 返回字段、来源和置信度 |
| `update_claim_field` | 更新业务字段 | 字段白名单、记录来源与版本 |
| `validate_claim` | 运行报销规则 | 返回阻断项和提醒项 |
| `get_claim_summary` | 获取汇总 | 后端计算金额 |
| `request_submission` | 生成确认快照 | 不改变提交状态 |
| `submit_claim` | 最终提交 | 必须满足确认、校验通过、版本未变 |

所有工具调用记录为结构化审计事件。票据文本、附件内指令和用户对话均为不可信输入，不能改变 Agent 的工具权限或系统规则。

## 6. 票据识别、校验与澄清

### 识别链路

1. 对图片/PDF 做格式、清晰度、旋转、页数和恶意文件检查。
2. 对票据进行分类与结构化 OCR/票据识别，优先提取票号、日期、购买方、销售方、金额、税额、价税合计和项目名称。
3. 保存原文件、原始识别结果、字段置信度和识别服务版本。
4. 由 Agent 解释结果、归纳待补项和建议费用类别；关键金额、日期、票号不由 Agent 无依据覆盖。

### 置信度策略

- 高：自动填入，用户可在确认页修改。
- 中：自动填入并标记为待确认。
- 低或冲突：不作为最终值，必须追问或手工填写。
- 阻断：文件不可读、关键金额缺失、疑似重复、关键主体明显不匹配时不可提交。

### 澄清策略

先询问阻断提交的问题，再询问跨票据共用的报销事由，最后询问单票特有字段（如餐饮参与人）。每轮只要求用户提供完成下一步所需的最少信息。无法可靠解析的凭证允许以“其他凭证”上传，并手填关键字段。

## 7. 数据模型与审计

- `Employee`：员工、部门、渠道身份映射。
- `ClaimDraft`：草稿状态、报销事由、合计金额、版本与待补项。
- `Receipt`：原始文件、内容哈希、票据类型、识别状态、识别结果与置信度。
- `ExpenseItem`：每笔费用的金额、日期、税额、类别、业务字段及字段来源。
- `Clarification`：问题、候选项、用户回答、关联字段与解决状态。
- `ValidationResult`：规则版本、校验结果、阻断/提醒级别和处置记录。
- `SubmissionSnapshot`：提交时不可变的完整报销单快照与编号。
- `AuditEvent`：识别、Agent 工具调用、字段变更、确认和提交事件。

原始票据、原始识别值和提交快照不可覆盖，只能新增版本。关键字段必须带来源：`识别`、`用户填写`或`系统计算`。附件内容哈希及发票关键标识重复时触发预警，不能静默合并。

## 8. 安全、权限与运营

- Web 与未来飞书账号映射至员工；员工仅能查看自己的草稿和附件。
- 附件设定类型、大小和页数限制，恶意文件扫描后私有存储，下载使用短时授权。
- Agent 只拥有白名单工具；每个工具校验身份、字段、草稿状态和参数。
- 提交须同时满足员工明确确认、规则校验通过和草稿版本未变化；金额由后端计算。
- 模型请求遵循数据最小化；日志脱敏身份证号、银行卡号和手机号，并制定附件、会话及日志保留期限。
- 监控识别失败率、字段修改率、平均澄清轮数、提交率、重复票命中率和后续财务退回率。

## 9. 交付阶段

### 阶段 A：Web 最小闭环

实现登录、草稿、附件上传、2–3 类高频票据识别、手工修正、报销事由澄清、汇总确认、提交、基础校验与审计。

### 阶段 B：Agent 与规则增强

增加多轮对话、置信度展示、可配置必填项和基础费用规则、多票据合并、失败重试和运营看板。

### 阶段 C：飞书渠道

飞书机器人接收消息和附件、映射员工身份、续办同一草稿并发送待补/进度提醒。复杂编辑和最终确认跳转 Web；所有渠道共享草稿、规则和审计链路。

## 10. 验收方案

使用脱敏历史票据覆盖清晰与模糊票据、单张与多张附件、重复票、识别修正、缺失业务字段、提交前修改和跨渠道续办。验收以员工是否能顺畅、可追溯地完成提交为主，模型识别率是过程指标而非唯一目标。
