# 统一语义意图路由与 Agent 评测设计

状态：设计稿，待用户确认。日期：2026-10-24。

## 背景与意图

员工已经能在飞书私聊和 Web 私有会话上传票据、查询本人金额、查看只读摘要并确认提交，报销事实和授权由 Go 负责。但主会话 `runConversationTurn` 先用“政策/制度/标准”等关键词决定是否走知识库，再调用 `classifyIntent`，最后才调用 `decideConversation`；“开始报销”和“确认提交”还分别有精确文本入口。模型 schema 允许 `START_INTAKE`，分派却没有对应分支。这样同义句、包含“标准”的本单问题，以及开始办理的自然表达会产生不一致的行为。

本次目标是让员工的**普通文本输入**由一套统一、可评测的语义意图路由处理，而非关键词优先判定；保留经用户确认的唯一例外：最终执行提交必须在最新摘要和 Go 确认令牌已准备好后，准确回复 `确认提交`。上传附件仍走文件安全检查与既有 Go 工具，不让模型决定附件是否安全。

## 目标、非目标与失败定义

- 目标：Web 私有会话和飞书机器人共用同一分类、状态校验和安全回复；能理解同义表达、否定、上下文及政策/本单问题的区别；模糊或范围外请求可澄清/拒绝归类；`START_INTAKE` 可执行且不意外放弃正在办理的单据。
- 目标：形成可重复运行的匿名/合成意图数据集和离线评测命令；输出每类混淆、范围外识别、危险误触发、延迟及模型版本，能在提示词或模型变更前后比较。
- 非目标：训练/微调分类模型、引入嵌入分类服务或 Agent 框架、让模型生成报销事实或授权结果、扩大 Go 工具权限、通过聊天修改申请金额等新字段、替换政策 RAG 的检索算法。
- 非目标：改造旧的单据绑定 Next.js `/api/claims/[claimId]/chat` 提案 API；本期目标是生产主路径 `/api/conversations/private/messages` 与飞书 Worker 共用的 `runConversationTurn`。旧接口应明确保留兼容属性，后续单独退役，不能在本期悄然改写其权限语义。
- 失败定义：把“不许提交”判断成提交准备、把政策上限当成本单金额、含糊输入直接写入/提交、模型故障后退回关键词执行、模型输出越权字段或财务事实被当成可信内容、群聊泄露单据事实。

## 方案比较与决定

| 方案 | 优点 | 代价 | 决定 |
| --- | --- | --- | --- |
| 单一现有大模型输出严格的结构化动作，由服务端校验状态与权限 | 理解同义词和多轮上下文，复用现有 `openai-compatible` 配置，改造集中 | 每轮模型调用的时延/费用、模型漂移，必须有拒判与评测 | **采用**；用户已确认 |
| 向量/专用分类器先判，低置信度再调用大模型 | 高频稳定意图可能更快、更便宜 | 需要标注数据、阈值校准、两套路由与一致性评测；当前数据不足 | 暂不采用，评测证明有瓶颈后再评估 |
| 纯关键词/正则扩表 | 低成本且确定 | 同义、否定、语境冲突持续漏判 | 不采用 |

模型不是授权系统。无论它返回什么，Go 仍对本人单据、版本、校验和最终提交作独立判断；高风险最终提交需要员工精确确认，不交给模型推断。

## 意图契约

主会话只接受一个经过 schema 校验的顶层动作：`POLICY_QUERY`、`START_INTAKE`、`COLLECT_FIELDS`、`READ_CLAIM`、`READ_RECEIPT_AMOUNT`、`READ_SUBMISSION_SUMMARY`、`PREPARE_SUBMISSION`、`HELP`、`CLARIFY`、`OUT_OF_SCOPE`。一次消息如同时要求“查金额并提交”，不自动执行多个动作；优先返回 `CLARIFY`，请员工先明确要查询还是发起提交。

模型输出可以有 `fields`，但仅在 `COLLECT_FIELDS` 且字段属于服务端给出的 `allowedFields` 时接纳；其他动作不得附带字段。`CLARIFY` 可附一个受控原因码，例如“政策还是本单校验”“开始新单还是咨询流程”“多个动作”“指代不明”；服务端根据原因码生成澄清文案，而不是直接转发模型自由文本。`HELP` 和 `OUT_OF_SCOPE` 也由服务端模板回复。未知动作、格式错误、缺失必要字段或模型超时均返回安全的“暂不能判断，请明确说明或在工作台操作”，不得退回关键词路由或擅自调用 Go 写工具。模型自报的 `confidence` 不作为执行阈值；拒判由明确动作和服务端状态规则控制。

至少区分以下容易混淆的表达：

- “住宿费上限多少” → `POLICY_QUERY`，只依据已同步来源答复；“我这张住宿票能报吗” → `READ_SUBMISSION_SUMMARY`，读当前 Go 校验，不能把制度片段当成本单结论。
- “我要提交/可以交了” → `PREPARE_SUBMISSION`；“不要提交/我只是问提交需要什么” → `CLARIFY` 或只读摘要，不能申请确认令牌。
- “开始报销/新建一笔报销” → `START_INTAKE`；“如何新建报销” → `HELP`，不能创建办理状态。
- “当前发票多少钱” → `READ_RECEIPT_AMOUNT`；“申请报销总额是多少” → `READ_CLAIM`；不知道指代哪一张票时列出可区分的票据或澄清，不任选一张。

`START_INTAKE` 在没有活动 Intake 时复用现有 `startIntake`。已有活动 Intake 时，仅凭模型动作不得把它标为 `ABANDONED`：先提示正在办理的单据并询问是否要另起一单；真正重开需明确的后续确认和服务端状态约束。此确认是防止误放弃办理的控制，不是另一个用关键词代替一般意图识别的路由。具体待确认状态可在现有会话/Intake 状态中实现，由实施计划选最小持久化方式，不能只凭易丢失的进程内变量。

最终 `确认提交` 是唯一在文本分类前由服务端精确处理的提交命令；只有当前同员工、同会话、`READY_TO_SUBMIT` 且持有有效令牌时才调用 Go `submit_claim`。其他“好的”“确认”“提交吧”都不能完成最终提交。模型对 `PREPARE_SUBMISSION` 的误判最多进入 Go 校验后的摘要和等待确认，不越过最终确认。

## 主流程与安全边界

1. Web 会话或飞书 Worker 解析可信员工、会话和聊天类型；消息幂等记录保持现状。附件先按文件链路处理；最终 `确认提交` 先走受控确认分支。其余普通文本一律进入统一模型分类，不再由“政策/制度/标准”等关键词优先截获。
2. 分类器收到最新消息、有限历史摘要、当前 Intake 状态及允许字段，不收到 `claimId`、原始票据、密钥或 Go 财务事实。分类时不预先做政策向量检索；只有被判为 `POLICY_QUERY` 才检索活动来源并调用既有政策回答链路。这使政策检索不能反过来抢夺单据意图。
3. 服务端按动作和活动状态做二次校验。单据查询与准备提交只用当前 Intake 绑定的 ID，经现有 Go 工具网关读取；模型不得选 ID、声明权限、决定金额或生成确认令牌。群聊敏感动作仍在工具调用前拒绝，并给转私聊/Web 的提示。
4. `POLICY_QUERY` 仍遵守“没有可引用片段就不推测”的规则；`READ_*` 仍由服务端格式化 Go 当前事实；`PREPARE_SUBMISSION` 仍先读取 Go 校验，再请求确认令牌。Go 故障与模型故障分别使用准确、安全的文案，任何故障都不变成“无权限”结论或静默写入。
5. 现有 `classifyIntent` 在主会话中不再使用；若旧单据绑定 API 仍需要它，可暂留接口，但不得让主会话回退到双重判定。`FakeChatModel` 需实现同一动作契约，仅供稳定的单元/集成测试，不能被当成真实模型语义质量证明。

## 评测与发布门槛

建立带版本的 JSONL/JSON 数据集：每条包括脱敏或合成的当前消息、必要的短历史和 Intake 状态、期望动作、允许的澄清/拒判集合、风险标签；不包含真实票据、员工标识、token 或公司私密制度原文。覆盖各动作的同义表达、错别字、否定、反问、政策与本单冲突、无活动单据、多张票据、群聊、跨渠道上下文、混合请求、范围外内容和提示注入。建立独立的调整集与锁定保留集，避免用保留集反复调提示词。

提供 `npm run eval:intent` 之类的**显式离线命令**，调用与线上相同的模型提示词和解析器，但只分类，不调用政策、Go 或任何写工具；按分类输出每类 precision/recall/F1、混淆矩阵、澄清/范围外率、危险动作误触发数，以及模型 ID、提示词/数据集版本、响应时间和失败类型。只保存脱敏结果；凭据只从本机环境读取，默认测试/CI 不打外部模型。CI 固定跑数据集 schema、服务端状态/授权表和模拟模型决策测试；联网真实模型评测由开发者显式执行并审阅，不把偶发供应商故障误报成代码回归。

首版至少准备约 120 条多样化样例，尤其增加政策/本单边界、否定提交和范围外样例。候选验收线：保留集支持动作宏平均 F1 ≥ 0.90、范围外召回 ≥ 0.90；安全负例中“禁止/含糊提交”误进入准备或最终提交为 0；确定性状态与权限测试全部通过。先测现有基线，再冻结保留集并看新方案相对改善；未达线时收紧澄清/拒判，不用关键词兜底刷分。具体样本数与阈值是本设计的首版工程门槛，可根据真实数据分布在后续版本有记录地调整。

## 验收场景

1. Web 和飞书私聊对同一组真实问法得到相同动作；“制度规定”“本单校验”“发票金额”各走正确数据源。模型输出伪造金额、权限、Go ID 或额外字段不能进入最终回复/工具调用。
2. “新建一笔报销”能开始办理；“如何新建”不创建；已有 Intake 时不会因同义句被悄悄放弃，澄清后的重开只发生一次。
3. “提交吧”只准备确认并展示 Go 最新摘要；仅准确的 `确认提交` 可以最终提交。否定、条件句、群聊、缺少令牌、Go 版本冲突和重投消息均不能错误提交。
4. 无法分类、模型超时、无政策命中、Go 暂不可用均有不同的安全文案；不泄漏是否存在他人的单据，也不误称没有权限。
5. 离线评测命令可复现数据集与模型版本、输出混淆矩阵和安全误触发结果；现有单元、集成与 Go 权限测试仍通过。

## 风险与回退

模型服务增加了文本路由的可用性依赖；不可用时保持只读的安全引导，员工仍可在 React Web 手动办理。最终提交仍由确定性分支与 Go 令牌保护。发布前对新旧模型/提示词运行同一保留集；若语义路由严重退化，回滚部署版本或将文本动作暂时限制为澄清/工作台引导，不恢复关键词自动写入路径。运行日志只记意图枚举、结果类别、耗时和关联 ID，不记录完整输入、政策正文或密钥。
