# 跨渠道报销 Agent 会话设计

## 1. 目标与范围

将 AI 报销 Agent 从“草稿详情页中的澄清控件”调整为员工可长期使用的跨渠道助手。员工可以在飞书单聊或 Web 悬浮对话框中询问报销政策、上传票据、补充缺失信息、生成报销单，并在明确确认后提交。

会话记录不以报销单号作为主归属。报销办理只是会话内发起的一项短生命周期任务；某条消息可以引用生成或提交后的报销单，但会话本身不会绑定单一 `claimId`。

本期包含：

- 员工跨渠道私有会话（Web 与飞书单聊共享）及飞书群聊隔离会话的持久化；
- 受控的报销办理任务（Intake），支持对话上传票据、补充字段、生成草稿与确认提交；
- Web 全局悬浮对话入口及历史回放；
- 飞书与 Web 的统一会话编排、政策 RAG 引用快照与审计边界；
- 移除报销草稿详情页中的专属 AI 澄清面板。

本期不包含：

- 多企业租户、财务审批、ERP/OA 对接；
- 模型自动提交、模型任意写字段或自动发布政策；
- 将群聊内容同步至员工 Web 私有会话；
- 上传任意附件但不创建报销办理任务的通用文件存储；
- 会话记录的手动删除、导出或运营后台检索界面。

## 2. 已确认产品规则

| 场景 | 规则 |
|---|---|
| 会话归属 | 会话按员工和安全范围归属，不按报销单号归属。 |
| Web 会话 | 每位登录员工有一个私有跨渠道会话，所有认证页面通过悬浮入口访问。 |
| 飞书单聊 | 绑定飞书账号后的员工在机器人单聊中续用该员工的私有跨渠道会话。 |
| 飞书群聊 | 仅处理 @机器人 消息；每个 `employeeId + chatId` 是独立会话，群聊内容不得进入 Web 私有会话或其他成员的上下文。 |
| 普通问答 | 政策问答不创建草稿或办理任务。 |
| 报销开始 | 用户输入“开始报销”或上传合规票据后，创建一项报销办理任务；首次票据处理时自动创建草稿以复用现有附件、OCR 和校验能力。 |
| 手动草稿 | 用户在 Web 手动创建或编辑的报销单不被 Agent 自动接管，也不展示详情页 AI 澄清卡。 |
| 缺失信息 | Agent 仅能向用户追问受白名单约束的字段；用户在办理任务中的明确回答可写入 Intake，之后由服务端写入对应草稿。 |
| 提交 | Agent 先生成提交摘要；仅当前有效 Intake 收到员工精确文本“确认提交”时，服务端重新校验并提交。 |
| 留存 | 会话消息及引用快照随员工账号保留；员工账号删除时级联删除。不会保存飞书 token、附件原件、对象键、完整 OCR 原文或模型内部提示词。 |

## 3. 架构选择

采用“独立会话 + 短期办理任务 + 既有草稿”三层模型：

```text
飞书单聊 / 飞书群聊@ / Web 悬浮球
                ↓
       AgentConversation + AgentMessage
                ↓
      意图路由：问答 / 开始报销 / 办理中 / 确认提交
                ↓
          ReimbursementIntake（短期状态）
                ↓
 ClaimDraft + Receipt + OCR + 校验 + SubmissionSnapshot
```

`AgentConversation` 与 `AgentMessage` 提供用户可回放的历史与模型上下文来源；`ReimbursementIntake` 保存本次办理的受限结构化状态；既有 `ClaimDraft` 仍是票据、费用明细、校验和提交的唯一业务事实来源。

这避免了把长期政策问答错误归属到某一草稿，也避免将模型摘要当作金额、票号或提交状态的事实来源。

## 4. 数据模型

### AgentConversation

字段：`id`、`employeeId`、`scopeKey`、`kind`（`PRIVATE` / `GROUP`）、`summary`、`summaryThroughSequence`、`lastActiveAt`、创建与更新时间。

- Web 私有会话与飞书单聊共用稳定的员工私有范围 `scopeKey`，并且 `kind=PRIVATE`；每位员工只有一个跨渠道私有会话。
- 飞书群聊使用 `chatId` 作为 `scopeKey`，并且 `kind=GROUP`。
- `employeeId + kind + scopeKey` 唯一，防止重复创建会话。
- `summary` 是模型上下文的压缩记忆，不是报销事实或政策事实来源。

### AgentMessage

字段：`id`、`conversationId`、单调递增 `sequence`、`role`（`USER` / `ASSISTANT` / `SYSTEM`）、`channel`（`WEB` / `FEISHU`）、`channelMessageId`（可空且唯一）、`text`、`citations` JSON、`result` JSON、`createdAt`。

- `citations` 仅保留标题、章节路径、证据摘录、检索相关度和安全原文 URL，作为回答时点的审计快照。
- `result` 可保存最小业务结果，例如 `claimId`、`intakeId`、提交编号或安全状态码；它不是会话的主关联键。
- 飞书入站消息借助 `channelMessageId` 与现有 `InboundChannelEvent` 幂等机制避免重复写入。
- 不保存附件二进制、对象键、原始飞书事件包、token 或完整 OCR 文本。

### ReimbursementIntake

字段：`id`、`employeeId`、`status`（`COLLECTING` / `READY_TO_SUBMIT` / `SUBMITTED` / `ABANDONED`）、`claimId`（可空）、`conversationId`、受限 `collectedFields` JSON、`pendingFields`、`submissionToken`（可空）、`lastUserConfirmationAt`、创建与更新时间。

- Intake 是办理任务，不是长期会话容器。
- 首次合规票据时创建草稿并填入 `claimId`；仅服务端受控用例可调用既有上传、提取、字段更新、提交和审计逻辑。
- 每位员工同时最多一个 `COLLECTING` 或 `READY_TO_SUBMIT` Intake；员工发送“开始报销”可放弃旧 Intake 并创建新任务，旧草稿不自动删除。
- 手动创建的草稿不创建 Intake，也不成为 Agent 的默认目标。

## 5. 上下文管理

完整消息历史与模型本轮上下文分离：

```text
AgentMessage 全量审计历史
        ↓
滚动摘要（覆盖至指定 sequence）
        ↓
最近消息窗口 + Intake 权威状态 + 本轮 RAG 片段
        ↓
本轮模型调用
```

每次模型调用只包含：

- 系统边界与可用工具；
- 最多约 1,500 tokens 的滚动摘要；
- 最近 8–12 条消息，最多约 3,000 tokens；
- 当前 Intake 的结构化状态，最多约 1,500 tokens；
- 本轮检索的 3–5 个政策分片，最多约 2,500 tokens；
- 至少约 1,000 tokens 的输出预留。

当消息窗口超出预算时，后台或同步用例将较早消息压缩为摘要并更新 `summaryThroughSequence`。摘要更新必须基于 sequence 条件更新，防止并发消息导致摘要倒退。金额、票据、字段确认、草稿版本和提交状态始终从 Intake/ClaimDraft 查询，不从摘要读取。

飞书群聊绝不与 Web 私有会话共享摘要或最近消息。飞书单聊与 Web 私有会话在本期共用同一会话，因此员工可在任一渠道续办自己的私有报销任务。

## 6. Agent 办理编排

新增 `runConversationTurn`，替代在草稿详情中直接调用 `runAgentTurn` 的做法。

1. 服务端依据认证员工、渠道范围和入站事件取得会话。
2. 追加员工消息，读取当前 Intake 与最近上下文。
3. 对政策问题执行现有检索和受约束回答；保存服务端返回的引用快照。
4. 对“开始报销”或附件触发，创建/复用 Intake；首次附件创建草稿后复用现有 `uploadReceipt`、`extractReceipt`、重复票、OCR 与规则校验。
5. 对办理中的补充答案，模型只能返回白名单字段建议；应用层验证字段、值、草稿归属和版本后写入 Intake，并通过既有字段更新用例同步至草稿。
6. 当校验通过时生成现有确认摘要并将 Intake 变为 `READY_TO_SUBMIT`。
7. 仅精确“确认提交”且 Intake 仍有效时调用现有提交用例；服务端再次校验确认 token、草稿版本、员工归属、票据与政策规则。成功后 Intake 标为 `SUBMITTED`。

模型不能创建任意草稿、绕过提交确认、写入非白名单字段、接受外部 claimId、修改手动草稿或读取其他员工的历史。

## 7. Web 与飞书界面

### Web

- 从报销草稿详情页移除 `ClaimChat`。
- 在认证应用外壳中加入悬浮入口，按钮具有可见标签、键盘焦点与窄屏可达性。
- 打开后展示私有会话最近历史、可展开的 RAG 证据、附件上传、进行中 Intake 状态和明确提交摘要。
- 历史初始加载、发送中、无历史、错误与提交成功均保持稳定布局；提交成功不自动关闭会话。

### 飞书

- 延续当前长连接 Worker、事件幂等、身份绑定与群 @限制。
- 文本回复保留简短答案、证据摘录、办理状态和工作台链接；不发送草稿字段写入、删除或提交的 URL 操作。
- 飞书“确认提交”是普通受控文本命令，不是隐式模型操作；命令失败时返回安全错误和工作台链接。

## 8. 权限、安全与留存

- Web API 仅以 session 中的员工身份读取私有会话、消息和 Intake。
- Worker 仅以已绑定的 `open_id` 找到员工；群 @过滤发生在读取/持久化正文前。
- 会话、Intake 和草稿读取均需员工归属校验；不可用浏览器提交的 `employeeId`、`conversationId`、`intakeId` 或 `claimId` 取代服务端查询。
- 会话数据随 `Employee` 级联删除；报销草稿删除不删除独立对话历史，仅将相关消息结果标记为历史引用。
- 接口、模型上下文、日志和飞书回复均不暴露凭据、对象键、附件二进制、其他员工内容或内部异常。

## 9. 验收标准

1. 员工可在飞书单聊或 Web 悬浮入口进行纯政策问答，且不创建草稿或 Intake。
2. 飞书群聊只有 @机器人消息产生该成员的独立群会话；群消息不会出现在 Web 私有历史。
3. 首次上传票据自动创建 Intake 和草稿，后续回答只补齐白名单字段；手动草稿不会被 Agent 自动修改。
4. Agent 会话历史可跨刷新回放，并展示保存时的政策引用快照。
5. 长历史只向模型传递摘要、最近窗口、权威 Intake 状态和即时 RAG 片段；摘要不能覆盖草稿事实。
6. “确认提交”以外的文本不能提交；确认时服务端重新验证草稿版本、归属、票据与政策规则。
7. 飞书事件重试不会重复写入消息、上传票据、创建草稿或提交报销单。
8. 删除草稿不删除独立会话；删除员工后会话、消息和 Intake 一并删除。
