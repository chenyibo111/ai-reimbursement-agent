# 报销政策中心与知识库设计

## 1. 目标与范围

在现有单企业 AI 报销系统中增加“结构化政策规则 + 飞书制度原文问答”能力。财务或政策管理员可维护可执行的报销规则，并显式同步指定的飞书新版文档或知识库 Wiki 页面。员工在 Web 工作台或飞书机器人中可以询问政策；报销单校验与提交则由确定性的规则引擎给出阻断或预警结果。

本设计的核心原则是：制度原文用于解释和溯源，结构化规则用于作出机器可执行的合规结论；大模型不得自行生成、修改或执行政策规则。

### 成功标准

- 管理员可维护草稿、发布和归档政策版本；一张报销单的校验和提交结果可追溯至准确的已发布版本。
- 第一版支持总额上限、费用类别单笔上限、允许费用类别、按类别必填字段以及每条规则的阻断/预警级别。
- 管理员可显式添加飞书新版文档或 Wiki 页面作为制度来源，手动同步后可在 Agent 对话中获得带原文链接的答案。
- 员工的报销校验只使用已发布的结构化规则；文档检索或模型暂时失败不会绕过已有规则，也不会误把猜测当成制度结论。
- 本地 Docker Compose 可使用 NVIDIA GPU 运行 BGE-M3；生产环境可不改业务代码地迁移到本地 CPU、独立 GPU 服务或经批准的托管 Embedding 服务。

### 不包含

- 自动从制度文本生成、发布或修改可执行规则。
- 飞书文档变更的实时 Webhook 同步；第一版为管理员手动同步，并为后续 Worker 定时同步保留边界。
- 通用 RBAC、跨企业租户、财务审批、付款或 ERP/OA 集成。
- 把任意飞书文档、员工私聊消息或票据原件作为知识库来源。

## 2. 已确认的产品与权限规则

| 场景 | 规则 |
|---|---|
| 管理员身份 | 由 `POLICY_ADMIN_FEISHU_OPEN_IDS` 环境变量中的飞书 `open_id` 白名单决定。白名单外登录员工仅可查看政策与自身报销单结果。 |
| 制度来源 | 仅管理员显式添加的飞书新版文档或 Wiki 页面可同步；系统不枚举或扫描企业飞书空间。 |
| 规则生效 | 仅 `PUBLISHED` 政策版本参与校验；发布后不能原地编辑，修改必须创建新的草稿版本后再发布。 |
| 合规结论 | 规则引擎输出阻断或预警；检索到的制度原文只能作为解释与引用。 |
| 历史追溯 | 校验结果和提交快照保留政策版本、规则代码和当时的规则摘要；后续制度更新不重写历史事实。 |
| Agent 回答 | 回答应包含“依据哪份制度、哪段内容”的链接或引用；没有已同步证据时明确说明无法确认，不编造政策。 |

## 3. 方案选择

比较过三种方案：

1. **只做文档 RAG 问答**：实现快，但自然语言回答不能可靠地决定是否允许提交。
2. **结构化规则 + 文档 RAG 问答**：规则提供确定性校验，文档提供可追溯解释，适合报销这类有阻断后果的流程。
3. **由模型自动抽取并执行规则**：维护成本低，但制度存在歧义、版本和例外情况，自动规则不应直接拦截员工报销。

采用第 2 种。模型可以帮助管理员理解制度、帮助员工定位条款，但规则的录入、审核、发布和执行必须留在受控服务端流程中。

## 4. 总体架构

```text
政策管理员
    │
    ├── 政策中心：规则草稿 / 发布 / 归档
    └── 飞书文档或 Wiki 白名单 → 文档同步 Worker
                                      │
                                      ├── 文档快照、切片、审计 → PostgreSQL
                                      ├── 原始导入附件（后续）→ MinIO
                                      └── Embedding Provider → pgvector 索引

员工 Web / 飞书机器人
    │
    ├── 报销校验、提交 → 确定性 PolicyRuleEngine → 阻断 / 预警 / 政策版本留痕
    └── 政策问答 → 检索已发布制度片段 → Chat Model → 带引用回答
```

`Web`、`feishu-bot-worker`、数据库和对象存储保持现有职责。新增的 `policy-sync-worker` 负责受控文档同步与索引；新增的 `embedding-service` 只将文本映射为向量。两个服务均不直接处理浏览器 Cookie 或报销写入授权。

## 5. 数据模型与版本边界

### 政策规则

- `PolicyVersion`：标题、状态（`DRAFT`、`PUBLISHED`、`ARCHIVED`）、生效日期、发布日期、发布人、创建与更新时间。发布事务保证同一时刻最多一个有效版本。
- `PolicyRule`：隶属版本、稳定规则代码、名称、规则类型、适用费用类别、配置 JSON、`BLOCKING`/`WARNING` 级别、显示顺序和启用状态。
- `PolicyRuleType` 第一版限定为：`CLAIM_TOTAL_MAX`、`CATEGORY_ITEM_MAX`、`CATEGORY_ALLOWED`、`CATEGORY_REQUIRED_FIELD`。配置由服务端 Zod schema 严格校验；不提供可执行脚本、SQL 或任意表达式。

发布后的版本和规则不可变。编辑发布版本会复制为新草稿，旧版本保留用于历史查询。规则删除、发布、归档和同步均写入独立的政策审计记录，保存操作者、动作、版本和最小差异摘要，不保存密钥或完整票据内容。

现有 `ValidationResult.ruleVersion` 将由固定字符串升级为发布政策的稳定版本标识；新增规则结果保留规则代码与可显示说明。`SubmissionSnapshot` 保存提交时的政策版本和规则结果摘要，确保重放与审计一致。

### 文档与向量索引

- `PolicySource`：来源类型（`FEISHU_DOCX` / `FEISHU_WIKI`）、管理员提交的 URL、资源 token、展示标题、启用状态、最后成功同步时间、源版本/内容哈希与安全错误分类。
- `PolicyDocumentSnapshot`：某次同步的不可变文本快照、来源版本、取得时间和状态。第一版仅保存必要正文及结构化标题；日后若导入文件附件，其原件存入 MinIO，不写入数据库字段。
- `PolicyChunk`：快照、段落序号、标题路径、文本、长度、来源定位信息和向量。向量列使用 PostgreSQL `vector` 类型，维度与当前 Embedding Provider 的模型配置绑定。

Prisma 管理普通关系字段。`vector` 列、`CREATE EXTENSION vector` 和余弦相似度查询使用迁移及参数化 `$queryRaw` 封装；任何用户输入都不得拼接为 SQL、表名、列名或向量文本。

## 6. 飞书文档同步

管理员在政策中心粘贴飞书新版文档或 Wiki 页面链接。服务端解析并校验 URL 类型，存储最小资源标识；同步器使用应用凭据读取获授权的文档内容。若当前应用无权访问、链接无效、文档为空或格式不支持，保留来源行并给出可读、可重试的错误，绝不删除最近一次成功快照。

同步过程：

1. 读取文档元数据与正文，规范化标题、段落和链接，不记录飞书访问令牌。
2. 计算内容哈希；与最后成功快照一致时跳过切片和向量重建。
3. 对变化内容创建新的不可变快照，按标题和段落边界切片，保留来源定位信息。
4. 批量调用 Embedding Provider，事务性写入新索引并切换当前可检索快照。
5. 写入同步审计与状态；部分失败时不暴露半成品快照。

第一版提供“立即同步”入口和后台异步任务。后续定时同步仅复用同一用例，不将飞书事件直接变成业务写入。

## 7. Embedding 与部署

定义 `EmbeddingProvider` 接口，业务服务只传入文本并获得固定维度向量。实现包括：

- `fixture`：仅用于测试与本地不启用知识库的开发场景。
- `bge-m3`：通过内部 `embedding-service` HTTP 服务调用本地 BGE-M3；Docker 首次启动下载模型，模型缓存使用命名卷持久化。
- `openai-compatible`：面向未来经合规批准的托管或私有 Embedding 服务。

初期 Compose 中的 `embedding-service` 与 Web、Worker、PostgreSQL、MinIO 同机运行，端口只暴露给 Docker 内部网络；GPU 可通过 Docker 的 NVIDIA runtime 挂载。生产中模型服务可迁至独立 GPU/CPU 节点，应用只调整 `EMBEDDING_BASE_URL`，不改变规则、索引或业务 API。

PostgreSQL 容器改用包含 pgvector 的 PostgreSQL 16 镜像，数据卷路径保持兼容。上线前执行备份、镜像演练和 `CREATE EXTENSION IF NOT EXISTS vector` 迁移；不得对已有生产卷执行破坏性重建。

## 8. 校验、Agent 与渠道边界

每次草稿校验、生成提交确认和最终提交均加载当前有效 `PolicyVersion`，在既有基础校验（必填、低置信度、重复票）后运行 `PolicyRuleEngine`。规则结果与基础校验统一映射为现有阻断/预警界面，但来源、规则名称和政策版本对员工可见。

- 阻断：禁止生成可提交确认或提交；明确展示规则与处理建议。
- 预警：允许继续，但在确认摘要和提交快照中留痕。
- 无已发布政策：保持现有基础校验，不伪造“已符合公司政策”；界面提示“尚未发布可执行政策”。

Agent 上下文新增只读的检索片段、来源标题和安全链接，不包含原始文档全量、飞书 token、数据库 ID、对象键或其他员工数据。模型回复必须基于返回片段；服务端验证引用属于检索结果，失败时降级为“当前没有可引用的已同步政策”。

飞书机器人将政策问答复用同一检索与回答服务；仍不允许飞书侧发布规则、确认字段、删除附件或提交报销单。群聊仅在 @机器人后处理的既有规则不变。

## 9. 管理与员工界面

- `/policies`：员工可读的当前生效版本、规则摘要和制度来源入口；管理员额外看到来源、同步状态与管理入口。
- `/admin/policies`：管理员创建版本、维护规则、发布/归档及查看审计。
- `/admin/policy-sources`：管理员添加飞书链接、查看上次同步、错误并触发同步。
- 报销工作台：校验面板按“基础校验 / 政策规则”分组，显示规则级别、当前政策版本、来源链接及可处理说明。
- Agent 面板：政策问题的回答显示简短引用卡片；回答不因缺少检索结果而给出确定性政策结论。

所有管理 API 在服务端按当前会话的 `Employee.feishuUserId` 执行白名单检查；浏览器传入的角色、`open_id` 或版本状态均不可信。发布、归档和同步请求使用乐观并发版本或不可变发布操作，避免管理员互相覆盖。

## 10. 配置、权限与安全

新增环境变量（均只存在于部署密钥文件，不提交 Git）：

```dotenv
POLICY_ADMIN_FEISHU_OPEN_IDS="ou_finance_a,ou_finance_b"
EMBEDDING_PROVIDER="bge-m3"
EMBEDDING_BASE_URL="http://embedding-service:8080"
EMBEDDING_MODEL="BAAI/bge-m3"
EMBEDDING_DIMENSIONS="1024"
POLICY_SYNC_ENABLED="true"
```

飞书自建应用按最小权限申请读取管理员显式授权的新版文档、Wiki 节点及其文档内容所需的范围；上线前由企业管理员审批并以实际开放平台权限名称为准。同步操作的日志只记录来源内部 ID、状态、切片数与安全错误分类，不记录 App Secret、access token、完整制度正文、附件字节或向量值。

输入链接、文档文本和模型输出均视为不可信。文档正文只能作为数据，不能影响系统指令、访问其他来源、执行工具或变更规则。检索片段要限制数量与长度，管理 UI 对正文执行安全渲染，禁止 HTML 注入。

## 11. 错误、冲突与恢复

| 场景 | 处理 |
|---|---|
| 非管理员访问管理 API | 返回 `403`，不泄露来源、版本或同步信息。 |
| 未配置/无有效发布版本 | 基础校验继续；政策区提示无有效政策，不产生虚假合规结论。 |
| 飞书无权限、链接失效或读取失败 | 来源标为失败并可手动重试；继续使用最近一次成功快照。 |
| Embedding 服务不可用 | 新同步不切换索引；已有快照和确定性规则继续使用；问答返回可恢复提示。 |
| 向量维度与索引不一致 | 拒绝切换快照并标记需要完整重建，不混用不同模型向量。 |
| 发布冲突 | 以版本条件拒绝旧请求，提示刷新后重新处理。 |
| 模型输出无有效引用 | 不显示猜测性答案，回退至“没有可引用的已同步政策”。 |

## 12. 验收与测试

1. 非白名单员工无法读取管理来源、创建/发布/归档版本或触发同步；白名单管理员的动作均留下审计。
2. 仅已发布版本参与校验；规则变更必须经新版本发布，历史校验和提交快照不被改写。
3. 每种第一版规则均覆盖阻断、预警、边界值、类别匹配与配置非法的单元测试。
4. 无政策、文档同步失败、Embedding 不可用和模型回答失败时，现有草稿校验、提交与 Agent 字段建议保持安全可用。
5. 同步只读取已注册来源；内容未改变时不重复嵌入，失败不替换上一次成功快照，切换时不暴露半成品索引。
6. 检索结果按相似度和来源过滤，回答只显示经过服务端验证的引用；员工无法通过提示词访问未授权制度或其他员工数据。
7. Docker 环境可启动 pgvector、Embedding、Web、飞书 Worker、OCR、ClamAV、MinIO；Embedding 服务不暴露公网端口，模型缓存重启后可复用。
8. 现有 OAuth、草稿、票据、OCR、Agent 建议、删除、提交和飞书机器人测试全部通过。
