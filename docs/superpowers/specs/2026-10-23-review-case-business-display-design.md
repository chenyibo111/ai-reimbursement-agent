# 财务复核案件业务化展示设计

## 目标

让财务人员能在复核队列中直接理解案件的业务含义，而不需要识别内部 ID、状态码或异常码。

## 已确认的展示规则

- 异常原因显示中文标题和可执行说明；未知原因使用安全的通用提示，不回退展示异常码。
- 关联报销单显示报销单号和报销事由，并提供通往该单据的真实链接。
- 领取人显示员工姓名；尚未领取时明确显示“尚未领取”。
- 财务页面不展示案件 ID、报销单内部 ID、票据 ID 或员工 UUID。
- 案件状态、领取、处理、审计、权限和版本并发控制保持不变。

## 方案

保留 `reasonCode` 作为服务端领域数据，在 React 层映射为已维护的中文业务文案；避免把可变的产品文案写死在 SQL 或领域模型中。

Go 的复核案件查询额外左连接 `claims` 和 `employees`，向客户端投影：

- `claimNumber`
- `claimPurpose`
- `assignedToDisplayName`

左连接和空字符串回退保证历史数据或已删除关联记录不会导致队列读取失败。领取、处理操作完成后仍返回同一业务化投影。

## 非目标

- 不新增或迁移数据库表。
- 不调整复核案件生命周期、审批权限或人工处理动作。
- 不把内部标识从审计记录或开发排障接口中删除。

## 验证

- Go HTTP 合同测试验证新字段使用 camelCase 输出。
- React 组件测试验证页面显示中文业务信息且不渲染原始异常码和内部 ID。
- 复用既有列表选择和报销单详情路由，不引入新的页面交互范式。

## 实施备注

**2026-10-23：已完成并本地验证。** 财务复核中心已按上述规则展示业务字段，且与领取、处理和原票预览动作共同通过本轮 Go/React 回归验证。
