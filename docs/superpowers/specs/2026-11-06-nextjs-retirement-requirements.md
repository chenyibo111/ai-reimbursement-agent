# Next.js 完整退役需求规格

- **状态：** 已确认，供实施计划与验收使用
- **日期：** 2026-11-06
- **适用范围：** `ai-reimbursement-agent` 仓库当前 `master`，报销 Web、Go API、Node Agent/Worker 与 Compose/CI
- **既定顺序：** 补政策来源管理入口 → 拆 Worker 构建 → 替换旧接口测试 → 删除 Next 专属代码与依赖 → 端到端验收。

## 1. 背景与目标

当前员工入口由 React 工作台、Nginx 边缘路由和 Go 报销 API 承担。Nginx 将 `/api/auth/*` 与 `/api/v1/*` 交给 Go，页面交给 React。旧 Next.js `web` 容器位于 `legacy-web` profile，默认不启动；仓库仍保留其页面、Route Handlers、构建步骤和大量路由测试。四个 Node 进程仍复用根 Dockerfile，该镜像运行 `next build` 并包含 `.next`。

本需求的目标是让日常构建、部署和运行完全不依赖 Next.js，同时保留当前 React/Go 报销能力以及飞书 Agent、政策知识库和异步任务。退役后仍允许 Node.js、TypeScript 与 Prisma 承载 Agent 领域数据；“删除 Next.js”不等于“删除 Node Worker 或 Prisma”。

成功状态：

1. 员工、管理员在 React 主入口可完成本规格列出的全部保留操作，不需访问旧 Next 端口。
2. 飞书机器人、Agent 事件、政策同步、任务和告警转发正常运行；Worker 构建不执行 `next build`，运行镜像不包含 `.next`。
3. 生产构建与部署配置不再包含 Next 应用、Next 服务或 Next 运行依赖。
4. Prisma 的 Agent 数据、员工身份关联及历史审计保持可读，既有报销单、票据和知识库索引不丢失。
5. 自动化和真实平台验收均有记录；旧 Next 停用后没有隐含的可写入口。

## 2. 范围与边界

### 必须保留

- React `/claims`、`/claims/new`、`/claims/:claimId`、`/admin/policies`、`/admin/reviews`，以及 Go `/api/auth/*`、`/api/v1/*` 的现有行为。
- 独立 `feishu-sso` 服务、Hydra、Go Auth BFF、同一员工身份和角色校验、统一退出。
- 飞书单聊和群聊边界、本人单据办理、受控确认提交、政策问答、票据识别与人工复核。
- Agent 会话、消息、Intake、幂等事件、异步任务、政策来源/快照/切片的 Prisma 数据和相关迁移。
- Go Auth BFF 现阶段读取的 `public."Employee"` 身份映射；删除 Next 时不得删除该表或擅自改变员工 ID。
- PostgreSQL、MinIO、NATS、OCR、Embedding、日志与告警的现有数据及持久化卷。

### 本次不做

- 把所有 Node Worker 或 Prisma 数据迁入 Go。
- 重写 Agent 意图识别、RAG、OCR 或报销核心规则。
- 接入真实审批、付款系统。
- 清空旧测试数据、重建数据库卷、删除历史迁移记录。
- 更换 SSO 提供方或改变员工可见范围。

## 3. 旧能力盘点与处置

实施前需以路由、调用方和存储写入为单位建立完整清单，并在 PR 中标注“迁移、保留于非 Next 服务、明确退役”之一。当前已确认的关键项：

| 旧入口或模块 | 当前处置要求 |
| --- | --- |
| Next 单据列表、新建、详情与提交页面/API | React + Go 已承担主路径；核对字段、错误码、权限和提交快照后删除旧实现 |
| Next OAuth/SSO 页面与 `/api/auth/*` | Go Auth BFF 已承接公共路径；核对双员工登录、续会话、退出、撤销和回调后删除旧实现 |
| Next `/admin/policies`、`/admin/reviews` | React + Go 已有对应入口；核对管理员/财务/员工的访问结果后删除旧实现 |
| Next `/admin/policy-sources` 与 `/api/admin/policy-sources/*` | **尚无 React/Go 主路径替代**；先交付新的管理页面与服务端接口 |
| Next `/policies`、旧政策规则和旧 Agent Web 对话 | 不作为当前业务事实来源；逐项确认没有保留需求、外部链接或仍在使用的调用方，再明确退役或提供跳转说明 |
| Next 员工角色管理 API、旧审核 API | 对照当前 Go 角色配置、复核中心和运维 CLI；如仍是唯一受支持的管理员操作，先补替代入口 |
| `src/ui/`、仅供 Route Handler 使用的 `src/server/` 文件 | 通过静态引用清单确认仅由旧 Web 使用后删除 |
| `src/application/`、`src/domain/`、`src/infrastructure/prisma/` | 按真实 Node Worker 调用图保留；不得因为位于旧目录就批量删除 |

清单必须覆盖全部 `app/` 页面和 Route Handlers、`src/ui/`、相关 `src/server/` 辅助代码、`public/` 资产、依赖与测试。对外仍需支持的旧深链应在新入口中有明确响应；不得把未知路径静默当作成功。

## 4. 功能需求

### R1：React 政策知识来源管理

1. 具有政策管理权限的用户可在 React `/admin/policy-sources` 查看已登记来源：标题、Docx/Wiki 类型、规范化原文链接、启停状态、最近成功同步时间、最近失败原因、当前章节数与切片数。
2. 管理员可登记已获授权的飞书 Docx/Wiki 链接，启用或停用来源，并手动请求同步；普通员工和财务复核员不得进行这些操作。鉴权必须在服务端按当前 SSO 会话和角色执行，不能仅依赖页面隐藏按钮。
   迁移前核对旧 `POLICY_ADMIN_FEISHU_OPEN_IDS` 与当前 Go/SSO 管理员角色；仅凭旧白名单取得权限的账号须显式完成角色授权或停止使用管理入口，不能自动扩大权限。
3. 链接沿用现有 `parsePolicySourceUrl` 的 HTTPS、`*.feishu.cn`、`/docx/{token}` 或 `/wiki/{token}` 约束；不接受任意 URL、重定向目标、凭据或查询参数。服务端负责规范化和去重。
4. 同步请求返回可追踪的任务 ID 与状态。界面明确区分“已排队、处理中、成功且有索引、原文未变化、失败”；不显示 `undefined` 切片数。刷新页面后仍能读取状态。
5. 无文档权限、文档不存在、文档结构不支持、Embedding 不可用等失败应显示可理解的分类；失败不得覆盖上次成功的活动快照。停用来源后，新的政策问答不得从该来源取证。
6. 原文在新标签页打开；来源内容、飞书凭据、向量和完整错误堆栈不进入浏览器响应或普通日志。保留审计记录中的操作者、来源、动作、结果和时间。
7. 页面与当前 React 管理页面保持导航、加载、空状态、错误、重试及无障碍交互一致；在网络失败或 401/403 时给出准确反馈。
8. 政策来源管理属于 Agent 知识库边界。服务端接口的具体部署位置在技术实施计划中确定，但必须复用现有 Prisma 仓储、异步任务与政策同步 Worker，且不能使 Go 报销 API 直接承担政策向量化逻辑。

### R2：Worker 专用构建

1. `feishu-bot-worker`、`job-worker`、`agent-event-worker` 和 `alert-relay` 使用独立的 Worker 构建目标；常规构建不执行 `next build`，运行镜像不复制 `.next` 或旧 Web 静态资源。
2. Worker 仍可使用当前 `tsx`、路径别名、生成的 Prisma Client、`services/agent`、配置和容器密钥入口；进程命令、信号转发、健康检查和容器内地址改写保持兼容。
3. 第一阶段可共享现有根 `package-lock.json`，只解决不必要的 Next 编译和输出复制；随后以独立包清单或等效依赖裁剪移除 Worker 镜像中的 Next/React 运行依赖。不能把“无 `.next`”误报为“无 Next 依赖”。
4. 相同源码版本构建出的四个 Worker 必须能按现有 Compose 命令启动，且不创建第二套数据库、对象存储或队列。旧 `legacy-web` 在最终退役前可作为显式回退目标；最终阶段移除。
5. 记录改造前后构建时间、构建产物大小和镜像大小；不预设比例目标，以可重复的同机同缓存条件比较。

### R3：接口与测试承接

1. 为 R1 新接口建立功能、鉴权、输入校验、任务状态和失败回退测试；现有 Worker 行为及 Go 报销/认证契约测试继续有效。
2. 逐项审查直接导入 `app/api/**/route.ts` 的旧 Next 集成测试。仍属于当前产品的断言迁到 React、Go 或独立 Agent 服务测试；确认退役的旧行为才可删除其专属测试。不得以整体跳过测试代替迁移。
3. 根仓库 CI 不再以 `next build` 为发布门槛，应构建 Worker 目标，并继续运行适用的 TypeScript、React、Go、数据库和路由契约检查。涉及真实平台的测试仍按现场验收执行。
4. 更新 README、启动命令、Compose 说明和运维手册；公开路径、端口、密钥边界及故障排查说明只指向仍可用的实现。

### R4：Next 专属代码和配置退役

1. 在 R1–R3 验收后删除 `app/`、仅由旧页面使用的 `src/ui/` 与 Next 专属服务代码、旧 UI 资产和 `legacy-web` Compose 服务。
2. 删除根包中的 `next`、`eslint-config-next` 等仅供旧 Web 使用的依赖及脚本；调整 `tsconfig`、ESLint、Dockerfile、`.dockerignore` 和 CI，使干净检出后无需 Next 即可安装、类型检查、测试与构建。
3. 保留 Worker 必需的 `react` 之外的实际依赖；是否可移除根包 `react`、`react-dom` 以引用扫描和构建验证为准。React 工作台在 `apps/web` 下继续独立维护自身依赖。
4. Prisma schema 与迁移按数据所有权保留；历史旧表的归档/清理是独立数据治理事项，不随代码删除执行。Go 对 `public."Employee"` 的依赖必须继续有效或经过单独的身份迁移设计与验证。
5. 完成后生产 Compose 不含 Next 服务，生产镜像不含 `.next` 或 Next 包，对外不存在可写的旧 Next API。

## 5. 非功能与安全要求

- **身份和权限：** 新政策管理接口只接受当前有效的员工会话与管理员权限；SSO 撤销、员工停用和角色变更后不得继续操作。服务之间不得信任浏览器传入的员工 ID 或角色。
- **数据一致性：** 来源启停、同步排队及活动快照切换保持原有幂等性与事务边界；重复点击、重复任务和 Worker 重启不生成互相竞争的活动快照。
- **失败恢复：** 飞书、Embedding、PostgreSQL 或队列故障时报告安全错误并可重试；已有成功索引继续可用，避免将故障提示误写为成功。
- **秘密与隐私：** `.env.local`、飞书 token、会话 Cookie、原票和政策全文不得进入构建层、公开响应、CI 日志或提交记录。Worker 继续通过现有受控密钥机制读取配置。
- **运行兼容：** 保持现有 Compose 项目名和命名卷；不得因拆镜像或删 Next 造成另起一套数据。当前 SSO 与报销仍是两个独立 Compose 项目。
- **可观测：** 保留 Worker 心跳、任务领取/完成/失败日志、关联 ID 与现有 Loki 告警；旧 Next 专属监控项按实际运行拓扑调整。
- **性能：** 新政策来源管理的列表与操作在正常本地数据量下无明显交互退化；不通过同步 HTTP 请求执行完整文档解析和向量化。

## 6. 分阶段交付与验收门槛

### 阶段 A：补政策管理入口

- React 页面和新服务端接口完整覆盖 R1；原有来源、活动快照和同步任务在新页面可见。
- 管理员可登记、停启、同步一份授权文档；无权限文档失败后仍可检索上次成功内容；普通员工访问返回 403。
- 旧 Next 服务停止时以上操作仍可完成。

### 阶段 B：拆 Worker 构建

- 四个 Worker 从专用目标构建，构建日志无 `next build`，镜像内无 `.next`。
- 飞书消息处理、任务领取和政策同步、Agent 事件通知、告警转发分别做启动与关键行为冒烟验收；失败重启与幂等记录保持正确。
- 完成依赖裁剪后，镜像依赖清单无 Next/React；构建和大小指标可与基线比较。

### 阶段 C：替换旧测试与清理 Next

- 有效业务断言在新接口测试中通过；旧路由测试有逐项迁移或退役记录。
- `app/`、`legacy-web` 服务和 Next 专属依赖删除；干净检出后的 CI 全部通过。
- 静态引用检查无生产代码导入 `next/*`、`app/**` 或旧 UI；Nginx 只路由到 React/Go/明确新增的 Agent 管理接口。

### 阶段 D：真实环境验收

- 两名企业成员分别完成登录、单据创建/查询、飞书办理和退出；互相查询得到授权拒绝。
- 管理员完成飞书文档登记与同步、政策问答引用、政策规则发布；财务完成票据复核；员工完成票据上传、OCR 和提交。
- 分别制造文档无权限、Embedding 暂不可用和 Worker 重启，确认错误提示、历史快照与幂等恢复。
- 记录版本、单号、任务 ID、预期/实际结果和日志关联 ID；不记录真实密钥、原始票据或完整会话文本。

## 7. 发布、回退与删除条件

1. 每个阶段独立发布并验证；阶段 A、B、C 不以删除数据卷或回滚数据库迁移作为回退手段。阶段 C 删除源码前保留可重新部署的上一个镜像和 Git 版本。
2. 旧 Next 页面仅在明确需要的过渡窗口由 `legacy-web` profile 手动启动；阶段 C 验收完成后才删除其服务定义。禁止重新暴露旧写 API 形成双写。
3. Go、React、Agent Worker 版本需配套发布。故障时回退到兼容当前数据库 schema 的整套镜像，保持新旧身份映射和历史记录不变。
4. 删除旧代码前确认：旧路由调用方清零；政策来源管理可独立运行；真实双员工验收通过；备份与恢复能力已验证；运维人员知道新入口和故障处置方法。

## 8. 待实施计划确认的技术决策

- 政策来源管理接口部署在独立 Agent 管理服务，还是由现有服务以受限代理承接；无论选择哪一种，Agent 数据所有权和服务端 SSO/角色校验必须满足 R1。
- Worker 独立依赖包采用 npm workspace 还是独立 package；以可复现锁文件、实际依赖裁剪和现有路径别名兼容为选择依据。
- 旧 `/policies` 和员工角色管理入口的使用情况及处置：已被新系统覆盖则退役；仍为唯一受支持操作则先补新入口。不得仅凭代码存在或默认未启动推定无人使用。

上述决策需在实施计划前完成路由/调用方盘点，不改变本文件的验收目标。
