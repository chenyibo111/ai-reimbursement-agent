# 跨飞书应用员工身份统一设计

## 目标与边界

同一企业员工从 React Web 的 SSO 登录和飞书机器人发消息时，应解析为同一个报销系统 `employee_id`，因而能访问本人同一批报销单。Web 登录仍由 OIDC SSO 完成，机器人仍验证飞书事件；两者不共享 Cookie 或应用 `open_id`。React 工作台不增加 Agent 对话入口。

本设计涉及 `ai-reimbursement-agent` 与相邻的 `feishu-sso` 两个仓库。现有报销单、Agent 会话、任务和审计记录不得因员工身份绑定而丢失。

## 当前状态

- Go Web 登录按 SSO 应用的 `feishu_open_id` 在 `public."Employee"` 和 `reimbursement.employees` 中建员工；机器人 Worker 按机器人应用的 `open_id` 在相同表中建员工。飞书对不同应用给同一用户不同的 `open_id`。
- SSO 飞书登录服务目前取得 `open_id`、名称和 `tenant_key`；机器人事件处理目前只持久化发送者 `open_id`。两侧均未取得同一企业内的 `user_id`。
- 报销 Go OIDC 客户端要求签名后的 ID Token 含 `feishu_open_id`；当前本地 SSO 的 Hydra consent 代码未把该声明写入 ID Token。身份统一前须补齐并验证这一基线。
- `public."Employee".id` 和 `reimbursement.employees.id` 在当前设计中共用系统员工 ID。`feishuUserId`、`feishu_user_id` 是旧的单值应用 `open_id` 字段，不适合作为跨应用主键。

## 选择的方案

**推荐并采用：企业内身份键 + 应用身份绑定。** 以飞书验证得到的 `(tenant_key, user_id)` 作为跨应用关联证据；系统内部继续以不可变 `employee_id` 作为业务主键。新增绑定表，唯一约束 `(tenant_key, app_id, open_id)` 和 `(tenant_key, user_id, app_id)`，每条绑定指向同一个系统员工。两个入口均由服务端使用本应用凭证向飞书取得/验证 `user_id`，不接受客户端自报的身份键。

备选 A：仅凭两个应用的 `open_id` 由管理员手工绑定。无需新增通讯录权限，但每名员工都要完成一次人工操作，错绑风险和维护成本较高。

备选 B：使用 `union_id`。仅在飞书确认两个应用属于同一应用提供方且两侧都能稳定取得相同 `union_id` 时可用；本项目不以此条件作为默认前提。

如果飞书权限或可见范围使某入口无法取得 `user_id`，该入口不得猜测、按姓名/手机号合并，也不得把既有员工的单据交给新身份。后续可提供已认证 Web 会话与机器人一次性验证码的显式绑定流程；本次自动关联链路应明确报错并保留原数据。

## 身份解析与授权

1. SSO 服务使用它自己的飞书应用凭证完成登录并验证 `tenant_key`，取得 `user_id`。Hydra 在同一次登录上下文向 ID Token 写入 `feishu_open_id`、`feishu_tenant_key`、`feishu_user_id`、`feishu_app_id` 和显示名。报销 Go API 验证签名、issuer、audience、nonce、会话 `sid` 和上述身份声明；缺失即拒绝建会话。`sub` 的现有含义保持不变。
2. 飞书机器人仅使用机器人应用凭证和事件中的发送者 `open_id` 向飞书查询同一企业的 `user_id`。请求失败或企业不符时拒绝读写报销数据。机器人回复仍使用自己的消息 API，不传递 SSO 应用的 `open_id`。
3. Go 身份服务在单个数据库事务内按 `(tenant_key,user_id)` 查找或创建系统员工，并绑定该入口的 `(app_id,open_id)`。`app_id`、`tenant_key`、`user_id` 必须由可信服务端提供，内部接口继续使用独立服务密钥。已有绑定与其他员工冲突时返回明确冲突，不覆盖。
4. Go Web BFF 和 Node Worker 均取得此服务返回的同一个 `employee_id`。业务查询、Agent 工具调用、权限和审计继续按系统员工 ID 工作；停用员工仍拒绝登录与机器人业务操作。角色由报销 Go 服务的员工记录决定，不能由机器人请求自行提升。
5. 旧 `feishuUserId`、`feishu_user_id` 字段暂保留供兼容和迁移，新的跨应用解析只以绑定表和企业身份键为准。所有依赖这两个旧字段的 Worker 路径迁移后才能删除它们。

## 已有数据迁移

先提供只读对账报告：分别解析历史 SSO 与机器人 `open_id` 的可信企业身份键，列出同一 `(tenant_key,user_id)` 下的两个员工 ID、各自的报销单数、会话数及其他引用。无法从飞书验证的旧身份只列为待人工处理，不自动合并。

对于已证实同人的重复员工，按稳定、可审计的规则选定一个 `employee_id`，在一个事务中迁移 `public` 和 `reimbursement` 的业务归属引用与应用绑定；历史审计引用保持原操作者 ID，旧员工记录取消飞书登录绑定并停用归档，另存旧新 ID 映射。角色或停用状态不一致、所有权或唯一约束冲突时回滚并要求人工复核。迁移工具默认 `dry-run`，实际执行前备份并显式指定匹配的员工 ID；不可静默批量改写。旧 SSO 会话需失效，要求重新登录。

## 验证与发布

- 单元与契约：两个应用不同 `open_id`、同一 `(tenant_key,user_id)` 得到相同员工 ID；不同企业相同 `user_id` 不合并；伪造 ID Token、缺少 `user_id`、权限失败、绑定冲突、停用员工均拒绝；同一事件重复投递和并发首次登录不生成重复员工。
- 集成：用户先通过 Web 创建草稿，再在飞书查询该草稿；反向先通过飞书创建，再在 Web 列表查看；另一名员工无法读取。核对财务角色与退出会话行为不变。
- 对账：执行迁移前后逐项比较员工、单据、附件、会话和任务引用的数量；迁移报告含回滚所需的旧新 ID 映射，不包含令牌或敏感凭证。
- 发布顺序：先为 SSO 与机器人应用确认读取 `user_id` 的权限和企业可见范围，再发布 SSO 声明、身份服务和两个入口，最后在备份后按审阅通过的映射迁移旧数据。若权限尚不可用，保留当前数据且不启用跨应用自动合并。

## 未纳入

React 网页 Agent 对话入口、真实审批与付款、跨企业员工自动合并，以及按姓名、邮箱或手机号猜测员工身份。
