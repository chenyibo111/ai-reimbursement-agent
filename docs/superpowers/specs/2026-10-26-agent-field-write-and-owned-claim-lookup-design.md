# Agent 字段写入与本人单据查询设计

**状态：用户已确认（2026-10-26）**

## 意图与范围

员工在飞书私聊或 Web 私有会话中补充报销信息时，Agent 只有在 Go 报销单真正保存并回读成功后才能说“已写入”。员工还应能查询本人已有单据，不必先在当前会话创建一笔新的报销。两项能力共享现有受控 Go 工具网关，不让模型直接调用数据库或决定授权。

本轮对话可修改的字段只有报销事由 `purpose`、费用类别 `expenseCategory`、参与人员 `participants`、项目编号 `projectCode`。申请报销金额、币种和备注仍在 Web 表单修改。查询已有单据为只读能力，不自动变更当前 `ReimbursementIntake.claimId`，不因此获得对旧单的提交权限。飞书群聊仍只允许非敏感政策问答。

不在本轮做：把会话编排迁入 Go、多币种、模型代填金额、审批流、全量历史单据分页界面或跨员工查询。

## 已有基础与方案选择

Go 已有按当前员工列单、按员工和 ID 读单、草稿版本化 PATCH，且 `claim_number` 全局唯一。Agent 已有员工绑定 Token、工具调用审计及幂等记录，但工具端口仅暴露 `purpose` 更新；会话 `COLLECT_FIELDS` 的其他字段目前只写入 Intake JSON。当前读取动作只认活动 Intake 绑定的单据。

- **采用：扩展现有 Go 工具网关。** 新增本人列表、本人单号精确查找和四字段类型化 PATCH；会话编排继续调用这一边界。改动集中，可沿用现有授权、审计和确认提交保护。
- **暂不采用：把会话状态机迁到 Go。** 可以进一步集中领域边界，但需同时迁移 Web/飞书会话、消息幂等、模型调用和知识库流程，明显超出本轮目标。
- **不采用：Next.js 或飞书 Worker 直接写 Go 数据库。** 会绕过已经确立的单写入方、授权与工具审计边界。

## 对话补字段

1. 模型只输出受控动作与类型化字段提案：`purpose`、`expenseCategory`、`projectCode` 为有界字符串；`participants` 为有界字符串数组。服务端根据当前 Intake 和字段白名单校验，拒绝空值、异常长度、未知字段或无法确定的人名列表；金额和备注不进入模型可写字段集。`allowedFields` 表示可编辑字段，不再误用只表示“仍需补齐必填项”的 `pendingFields`。
2. 仅收到“开始报销”仍只建立 Intake，不创建 Go 草稿。收到第一条有效字段补充时，若尚无 `claimId`，才创建 Go 草稿并绑定；有 `claimId` 时读取当前 Go 版本再 PATCH。这样对话中的明确填单动作会形成真实草稿，而非仅存 Intake JSON。上传票据仍复用该草稿；直接上传票据仍按现有流程建草稿。
3. 同一次消息提出的字段尽可能合并为一次版本化 PATCH。新建草稿时可在 create 中写入事由，其他字段随后的 PATCH 写入。Go 是真实来源：PATCH 返回后再按本人权限回读，只有回读值与提案一致才更新 Intake 的 `collectedFields`、清除相应 `pendingFields` 并回复“已保存到报销草稿”。若中途失败，只报告已核实保存的字段；未核实的字段明确说“未确认写入，请到工作台核对或重试”，不得笼统回复“已记录”。
4. `READY_TO_SUBMIT` 状态下任何允许字段的成功修改都清除旧提交 Token 与预览，并回到 `COLLECTING`；后续必须重新获取 Go 校验和提交确认。Go 的草稿状态、所有权、版本冲突仍由服务端最终裁决。遇到版本冲突时先回读，若目标值已一致可安全视为完成，否则提示重新核对，不盲目覆盖 Web 刚作出的修改。
5. 旧 Intake 中已有但未写入 Go 的非事由字段不能直接当作已保存。首次碰到这类记录时以 Go 回读为准，明确标注未保存字段并要求用户重新确认，不静默回填或覆盖当前单据。

## 查询本人已有单据

1. 意图增加 `LIST_CLAIMS`；模型可为读取类动作提取**报销单号**，但它仅是查找条件，不能成为授权依据。服务端先校验单号格式，再通过 Go 的本人范围查询。当前 Go 列表支持最多 100 项；为避免旧单因列表截断而“查无此单”，给列表增加精确 `claimNumber` 查询路径，并在 Go repository 中始终同时过滤 `owner_id`。未找到与无权限统一返回安全的“不存在或无权访问”。
2. “我有哪些报销单”只展示最近少量本人单据的单号、状态和事由；列表不展示附件或敏感明细。用户提供明确单号时，Go 精确查找后在私有会话中保存单独的 `selectedReadClaimId`。后续“这单金额/票据/状态”等只读问题可使用该选择，且每次读取仍由 Go 按员工身份校验。无明确对象且存在多个候选单据时请求用户给出单号，不凭模型猜选。
3. 显式选择的旧单优先作为只读问题的目标；没有只读选择时才回退到当前 Intake 单据。开始一笔新的 Intake 时清除旧只读选择，避免“本单”指代混淆。只读选择**绝不**改变 Intake 的写入/提交目标；`COLLECT_FIELDS`、准备提交及精确“确认提交”仍只作用于当前活动 Intake。已提交或非草稿单据不允许 Agent 修改。
4. Web 私有会话和飞书单聊共用员工私有会话选择；群聊不得列出或读取本人单据。会话中的单号、ID 和模型字段都视为不可信输入；API 不返回其他员工的存在性信息。

## 接口与数据边界

- Go：复用 `GET /api/v1/claims` 的本人列表，增加可选精确 `claimNumber` 过滤；保留现有 `GET /api/v1/claims/{id}` 的本人校验和 `PATCH /api/v1/claims/{id}` 的草稿版本校验。不增加 Agent 专属的绕权数据库读取。
- Agent 工具端口：类型化 `list_owned_claims`、`find_owned_claim_by_number`、四字段 `update_claim_fields`；所有调用携带现有 actor/channel/conversation/tool-call 身份与审计信息。模型不能自行填充 `actorEmployeeId`。
- 同一对话回合中的“写入前读取”和“写入后回读”必须使用不同且稳定的工具调用 ID；现有完成结果缓存不能把写入前快照错误复用为回读结果。重放同一回合仍须复用各步骤原有 ID 和幂等键。
- 会话持久化：为 `AgentConversation` 增加 nullable `selectedReadClaimId`，只保存 Go ID，不建立跨 schema 外键。模型上下文只提供必要的单号/状态摘要，不把 Go 身份令牌或其他员工数据放进提示词。
- 可观察性：记录动作类别、成功/失败码、工具耗时和请求关联 ID；不把字段值、参与人员、完整消息、票据内容或 Token 送入日志。

## 验收与回归

- 飞书/Web：先“开始报销”，补充四类字段后看到草稿；刷新 Web 工作台，Go 实际字段一致。金额和备注修改请求应引导去 Web，不能回复已保存。
- 未给字段时不建草稿；字段写入失败、版本冲突、非草稿修改时不回复“已记录”；字段成功修改后旧提交确认失效。
- 员工可列出本人最近单据、按精确单号查到较早单据、在后续一句中继续只读查询；他人单号和不存在单号显示同样安全结果。群聊不泄露列表或详情。
- 有进行中的 Intake 时查询旧单不会更改该 Intake；随后补字段和“确认提交”只能针对原活动办理单。飞书事件重放与 Web 重试不能重复创建草稿或重复 PATCH。
- 单元测试固定模型输出解析、字段白名单、指代和错误回复；Go 服务/仓储测试固定本人过滤与草稿版本；集成及端到端测试覆盖跨 Web/飞书会话、工具幂等和提交令牌失效。人工用两个不同员工身份作越权验证。

## 待实施者决定

具体字符串长度上限与参与人员数量上限，在不放宽 Go 现有约束的前提下由实施者定值并固定在测试中；查询列表默认展示条数也由实施者定值。不得改变以上授权、写入真实性和只读目标隔离原则。
