# 飞书报销机器人 Worker 设计

## 1. 目标与范围

为现有 AI 报销 Web 增加飞书机器人渠道。员工可在飞书单聊机器人，或在群聊中 @机器人，发送文本、图片、PDF 或文件来创建、续办并了解报销草稿。机器人复用现有草稿、附件上传、安全扫描、MinIO、PaddleOCR、Agent 建议、校验和审计能力；复杂编辑、字段建议确认、删除与最终提交仍在 Web 工作台完成。

首期目标是让员工自然地以“发送票据给机器人”作为报销入口，同时不复制或削弱 Web 的服务端权限与确认边界。

不包含：

- 在飞书内接受字段建议、删除票据或提交报销单。
- 财务审核、审批、付款、ERP/OA 对接。
- 群聊全量消息读取与处理；群聊只处理 @机器人的消息。
- 多企业租户管理和跨企业草稿访问。

## 2. 已确认的产品规则

| 场景 | 规则 |
|---|---|
| 群聊触发 | 仅处理明确 @机器人的消息；未 @ 的群消息忽略。 |
| 首次身份 | 员工尚未通过 Web 完成飞书 OAuth 绑定时，仅回复登录链接，不自动创建员工或草稿。 |
| 首次票据 | 已绑定员工在没有当前草稿时发送文本或附件，自动创建草稿并回复工作台链接。 |
| 草稿路由 | 每个“员工 + 飞书会话 chat_id”绑定一张当前草稿；单聊、群聊互不共享。 |
| 新草稿 | 员工发送 `新建报销` 时创建新草稿并替换当前会话绑定。 |
| 草稿查看 | 员工发送 `查看当前草稿` 时返回当前会话草稿的 Web 工作台链接。 |
| 字段与提交 | Agent 只能提出建议；员工必须在 Web 中确认建议、删除内容或提交。 |

## 3. 架构

采用飞书长连接模式。新增独立常驻进程 `feishu-bot-worker`，与 Web 使用同一代码仓、数据库、MinIO 和服务端配置，但不作为浏览器请求处理器。Worker 使用飞书自建应用凭据建立连接，接收 `im.message.receive_v1` 事件后将它们转换为受控的应用层操作。

```text
飞书事件（文本 / 图片 / 文件）
        ↓
FeishuBotWorker：事件解析、员工映射、幂等与会话路由
        ↓
既有应用服务：创建草稿 / 上传票据 / OCR / Agent / 校验
        ↓
PostgreSQL + MinIO + 审计事件
        ↓
FeishuReplyClient：进度、待补项、Web 工作台链接
```

长连接适合本地开发和 Docker 部署：开发时不依赖公网回调地址；部署时新增同镜像的 `feishu-bot-worker` 服务。未来如需改为公网 Webhook，只替换事件接收器，复用事件规范化、幂等、路由与业务处理服务。

## 4. 数据模型与幂等

新增两个持久化实体：

- `InboundChannelEvent`：存储渠道、飞书事件 ID、消息 ID、接收时间、处理状态、有限的失败代码和关联草稿 ID。事件 ID 与消息 ID 建立唯一约束。不得保存附件字节、飞书令牌、完整原始消息正文或对象键。
- `FeishuConversation`：存储 `employeeId`、`chatId`、当前 `claimId`、最近活动时间。`employeeId + chatId` 唯一。

Worker 接收事件后，先创建或读取 `InboundChannelEvent`：

1. 已存在且已成功处理的事件直接忽略，不重复创建草稿、上传附件或调用 Agent。
2. 新事件快速持久化为待处理状态；飞书连接处理器随后确认接收。
3. Worker 处理完成后更新事件状态并记录最小处理结果。
4. 处理失败时保留可重试状态。业务成功但飞书回复失败时，不回滚已保存的草稿或票据。

Worker 重启后从待处理或可重试事件恢复；同一事件在任意重试下最多产生一次业务写入。

## 5. 身份与会话路由

从飞书事件读取发送者 `open_id` 和 `chat_id`。仅使用当前飞书自建应用产生的 `open_id` 查询既有 `Employee.feishuUserId` 映射；不接受消息正文、显示名或客户端传入的员工 ID 作为身份依据。

未找到员工时，机器人回复带有 `FEISHU_REDIRECT_URI` 对应登录入口的 Web 链接，并终止本次业务处理。员工完成 OAuth 后，现有登录流程负责建立或恢复 `open_id` 映射。

已绑定员工的路由顺序为：

1. `新建报销`：创建草稿，更新会话绑定。
2. `查看当前草稿`：读取会话绑定并返回链接；无绑定时提示发送票据或使用 `新建报销`。
3. 普通文本或附件：读取会话绑定；无绑定时创建草稿并绑定；随后执行对应处理。

草稿所有权仍由既有服务端授权层复核。Worker 不能通过 `claimId`、`chatId` 或消息内容访问其他员工草稿。

## 6. 消息与附件处理

### 文本消息

Worker 将规范化文本与当前草稿上下文交给既有 Agent 用例。回复内容只能包含澄清问题、校验进度和服务端已经持久化的建议摘要。若有待确认建议，机器人回复“请在工作台确认”的链接，不创建飞书侧确认回调。

### 图片与文件消息

Worker 使用飞书消息资源接口按 `message_id` 和资源 key 下载二进制流。下载后再次执行文件大小、MIME 与扩展名校验，随后调用既有受控上传用例：安全扫描、私有 MinIO 存储、OCR 提取、费用明细创建和重复票校验全部复用，不实现渠道专用的旁路上传。

机器人先回复“附件已接收，正在识别”，再在处理结束后回复成功、失败或待人工确认状态。附件原文、对象地址、OCR 原始文本和访问令牌不得进入模型上下文、飞书回复或普通日志。

## 7. 飞书回复与 Web 边界

首期使用文本或交互卡片表达以下信息：

- 当前草稿编号与已接收附件名称。
- OCR 状态、待补项、重复票或低置信度提示的摘要。
- Agent 的澄清问题或建议摘要。
- “打开工作台”链接，指向 `/claims/{claimId}`。

只有 Web 工作台提供“接受并写入”“忽略建议”“删除附件”“删除草稿”“生成确认摘要”和“提交”。飞书卡片不得携带能够调用这些写入接口的操作值，也不得借由 URL 绕过现有登录、归属、版本校验或审计。

## 8. 安全与运行配置

新增以下服务器环境变量，全部不得提交到 Git：

```dotenv
FEISHU_APP_ID="cli_xxx"
FEISHU_APP_SECRET="..."
FEISHU_BOT_ENABLED="true"
FEISHU_EVENT_DELIVERY="long_connection"
APP_PUBLIC_URL="https://reimbursement.example.com"
```

飞书开放平台中启用机器人能力，按最小权限开通单聊消息、群聊 @机器人消息、收发消息与消息资源下载，并订阅 `im.message.receive_v1`。本地开发使用测试企业；上线前创建应用版本并由企业管理员发布。

凭据只在 Worker 和服务端 API 内使用。Worker 日志仅记录内部事件主键、处理状态和安全的错误分类；不记录 App Secret、tenant access token、附件字节、完整消息正文、对象键或发票字段。

## 9. 错误、冲突与恢复

| 场景 | 处理 |
|---|---|
| 重复事件 | 返回已处理结果，不产生第二次业务写入。 |
| 未绑定员工 | 回复 OAuth 登录链接，不建草稿。 |
| 不支持或超限附件 | 回复可读错误，不上传、不调用 OCR。 |
| 下载、安全扫描、MinIO、OCR 或模型失败 | 记录可重试状态，保留草稿和已成功附件，回复失败摘要与工作台链接。 |
| 草稿版本冲突 | 不覆盖新数据，回复“草稿已更新，请在工作台查看最新状态”。 |
| 飞书回复失败 | 业务事实保持，记录待重试回复；不得回滚草稿或票据。 |
| Worker 断线或重启 | SDK 重连；持久化待处理事件由 Worker 恢复。 |

## 10. 验收与测试

1. 未绑定 `open_id` 的单聊或群聊 @消息只得到登录链接，数据库不创建员工或草稿。
2. 已绑定员工首次发送文本或合规附件时，创建且只创建一张草稿，并绑定对应会话。
3. 同一事件重复投递不会重复创建草稿、附件、费用明细、Agent 建议或审计事件。
4. 群聊未 @机器人消息不会被读取或处理；@消息可正常续办该群会话草稿。
5. 图片、PDF、普通文件均复用既有上传、病毒扫描、MinIO、OCR 与重复票校验；超限或不支持附件被拒绝。
6. Agent 建议、低置信度和阻断校验在飞书只展示摘要及 Web 链接；飞书不存在确认、删除或提交成功路径。
7. Worker 重启、飞书下载失败、OCR 失败、模型失败、回复失败和版本冲突均有可重试或可恢复行为。
8. Docker 环境同时运行 Web、Worker、PostgreSQL、MinIO、ClamAV 与 OCR 服务；Worker 只需出网访问飞书，Web 工作台链接由员工浏览器访问。
